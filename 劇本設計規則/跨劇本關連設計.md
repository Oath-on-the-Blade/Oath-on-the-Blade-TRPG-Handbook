# 跨劇本關連設計

本文件規範**一般劇本之間**的前傳、後傳、平行、承接、共享事件、揭曉或其他明確跨劇本關連。其目的不是把所有關連劇本改造成戰役，而是要求每一份新關連劇本在自己的既有關連樹／關連圖中保持自洽，並在題材自然成立時容許一份新劇本同時連接多份既有劇本。

正式戰役內部的總綱、篇章接口、campaign state 與戰役級 NPC 主鍵仍以 `戰役總劇本設計.md`、`戰役劇本師規則.md` 為權威；若戰役階段另外宣告與戰役外的獨立劇本建立關連，該外部關連才同時受本文件約束。

---

## 1. 何時觸發

只要當前劇本宣告與任何已完成劇本存在以下任一關係，就必須使用本模組：

- 前傳；
- 後傳；
- 平行關連；
- 承接／延伸；
- 共享同一事件、人物、物件或局部歷史，且該共享內容會影響兩篇以上劇本的真相、狀態或玩家理解；
- 後作揭曉、重解讀或補充前作已建立的局部事實；
- 其他正文明確宣告的跨劇本關連。

單純同在同一道、同用某門派、同引用世界知識庫固定人物，**不自動構成跨劇本關連**。只有當本篇對另一篇的劇本專用真相、既有事件結果、跨劇本 NPC、局部世界狀態或敘事因果有實際承接時，才建立關連邊。

---

## 2. 關連圖與關連樹目錄

### 2.1 直接關連邊

「直接關連」指本篇明確與另一份劇本建立一條前傳／後傳／平行／承接／共享事件等關係。

例如：

- A → B：B 是 A 的單一後傳；
- A ∥ B：A 與 B 是平行關連；
- A → C ← B：C 同時承接 A、B；
- A — B — C：C 沒有直接連 A，但三篇仍位於同一個關連 component。

**單一延伸完全合法。** 本規則不要求每份關連劇本都同時連兩篇以上既有劇本。

### 2.2 關連 component

對當前劇本而言，從任何直接關連來源出發，沿 repo 中已明確宣告的跨劇本關連邊遞迴追查，直到不再發現新節點；所得全部劇本稱為本篇的**關連 component**。

建立 component 時，關連方向只用來理解時間與因果，不用來限制搜尋。作者必須同時尋找：

- 來源劇本自己宣告的前傳／後傳／平行／承接；
- 其他劇本反向指向來源劇本的關連；
- 以劇名、`script_id`、`@前作劇名`、關連定位／關聯來源欄位建立的既有連結；
- 關連樹目錄內的其他任務，以及任務正文指向的其他關連樹。

因此，不能只讀「我選中的那一篇前作」便假定它是一個孤立節點。

### 2.3 第一個關連任務時才建立關連樹目錄

一份獨立任務在尚未有任何關連任務時，**不需要預先建立空的關連樹目錄**。

當它第一次產生一份前傳、後傳、平行、承接或其他直接關連任務時，才建立關連樹目錄。目錄名稱固定為：

`_任務_<根任務名>_關連樹目錄/`

例如根任務為《三盞閘燈不能同時熄》，第一次新增關連任務時建立：

`_任務_三盞閘燈不能同時熄_關連樹目錄/`

此處的**根任務**是「在第一個關連任務建立時，被選作原始延伸基準的那份既有任務」。它是**歸檔根**，不要求永遠是世界時間最早的一篇；之後即使再創作更早的前傳，也不因此改名或換根。

建立目錄時：

1. 將根任務與第一份關連任務歸入該目錄；
2. 之後以這棵樹為主要來源創作的新關連任務，預設繼續存入同一目錄；
3. 若移動既有根任務會影響 repo 內已存在的相對路徑／明確連結，建立目錄的同一變更必須同步修正那些 repo 內部連結；不得留下已知斷鏈；
4. 目錄名一經建立即視為該樹的穩定歸檔名稱，不能只因後來多出新前傳、分支或跨樹關連而改名。

既有舊劇本若在本規則生效前已形成關連但仍散放於 repo 根目錄，不要求單獨為了規則改版立即大規模搬檔；**下一次為該關連樹新增任務或進行結構性維護時**，應補建上述目錄並一次完成該樹的歸檔與連結修正。

### 2.4 每個任務只有一個主要歸檔樹

一份劇本檔不得為了表示多項關連而在兩個或更多關連樹目錄各複製一份。每個任務只有一個**主要歸檔樹**。

新任務若以某棵既有樹中的節點作主要延伸基準，就存入該樹目錄。若創作一開始就同時涉及多棵樹，作者可按主要委託來源、主要因果承接或使用者指定決定一棵主要歸檔樹；其他樹只作跨樹關連來源，不建立重複檔案。

### 2.5 跨樹關連只建立指向，不合併目錄

若樹 A 中某份關連任務又與樹 B 的一份或多份任務建立實質關連：

- 該任務仍留在自己的主要歸檔樹；
- 在該任務的「直接關連來源／關連定位」中，同時指向樹 B 的相關任務；
- 樹 A、樹 B 的目錄名稱與歸檔根均保持不變；
- **不需要**把兩棵樹合併成一個新目錄；
- **不需要**為同一任務在另一棵樹再放一份副本；
- **不要求**只為建立跨樹邊而倒改另一棵樹的所有既有劇本；只要本篇關連任務的指向足以唯一辨認另一棵樹及實際相關節點即可。

因此，多棵關連樹可以透過任務間的直接關連形成更大的 component，但 repo 歸檔仍保持各自穩定。

### 2.6 關連樹不是戰役

關連 component 可以是一棵樹，也可以形成有多條邊的圖；repo 中也可以由多個穩定關連樹目錄透過跨樹邊構成更大的 component。這些情況都不因存在三篇、四篇或更多相連劇本而自動升格為戰役。

除非另有正式戰役總劇本，component 內每份 `independent` 劇本仍各自獨立開局、獨立完成、獨立結算；玩家也不需要按某個固定順序把整個 component 全部玩完。

## 3. 作者在創作前必須建立關連盤點

選定直接關連來源後，先完成以下盤點，再開始新增本篇世界真相。

### 3.1 找出完整 component

先檢查來源所在的 `_任務_<根任務名>_關連樹目錄/`；再以劇名與 `script_id` 搜尋 Community Scripts／權威劇本庫，追查該目錄內任務指向的其他樹與所有已宣告關連。每發現一個新節點，就再追查它的直接關連，直到 component 閉合。

若 repo 內沒有任何其他反向、旁支或跨樹關連，component 可以只有本樹內的少數節點；這不構成問題。

### 3.2 建立作者用關連帳

關連帳是創作工作資料，不要求作為額外交付檔。至少記錄：

- 劇本名稱與 `script_id`；
- 所屬主要關連樹／歸檔根；
- 與本篇及其他節點的直接關連類型；
- 世界內先後／平行時點；
- 已明確成立、後作不得無聲推翻的客觀事實；
- 仍刻意未知、只屬傳聞或尚未定案的事項；
- 各主要 `ending_id` 可能留下的持久狀態；
- 跨劇本 NPC 的穩定識別鍵／既有 alias；
- 會被多篇共同使用的地點、文書、物件、勢力狀態；
- 哪些 branch state 只在特定玩家履歷／存檔成立。

### 3.3 閱讀深度

以下劇本必須完整讀取：

1. 本篇所有直接關連來源；
2. component 中任何其真相、`ending_id`、NPC 身份、物件去向、地點狀態或時間線會實際影響本篇的節點；
3. 任何作者無法只靠關連定位／結局段確認是否與本篇衝突的節點。

對其餘 component 節點，至少必須核對其關連定位、GM 真相、相關 NPC、主要結局與會延續的世界狀態。若仍有疑義，升級為完整讀取。

---

## 4. 關連圖一致性是硬規格

### 4.1 已建立的客觀事實不能被無聲改寫

component 內已由既有劇本 GM 真相明確建立的客觀事件、責任、身份、死亡、生還、物件來源、地點結構或局部歷史，本篇不得因需要新的反轉而直接改成相反答案。

後作可以補充前作沒有回答的空白、揭示前作人物當時不知道的更深一層事實、重解讀同一批已存在線索，或證明前作角色／NPC 的推論有誤；但必須保留前作已明確成立的客觀事實。若新設計真的需要改寫既有客觀答案，應先修訂來源劇本／共同規則並處理版本與相容性，不能只在新篇偷偷 retcon。

### 4.2 分支結果必須保持分支

若來源劇本有多個 `ending_id`，本篇不能把其中一個結局當成所有桌共同歷史，除非本篇明確是有前置要求的 `continuous` 承接，且玩家介入條件已限定必須來自該結局。

對 `independent` 關連劇本，至少提供：

- **無前作紀錄基線**：沒玩過來源劇本仍可完整運行；
- **有紀錄覆蓋**：只有當該角色／該桌存檔實際具有對應 `ending_id` 或持久 state 時，才套用差異；
- 不相關或無法可靠歸因的舊紀錄不得被硬套成本篇事實。

### 4.3 同一 component 不等於同一桌都發生過

component 是**作者一致性範圍**，不是玩家必然履歷。作者要確保相連劇本可以在同一世界模型中互不矛盾；GM 實際運行時，只讀入該角色／該桌真正存在的履歷與 save，不得因兩篇同屬 component 就假定玩家一定玩過另一篇。

### 4.4 跨劇本 NPC 必須沿用既有身份

跨劇本 NPC 的基本識別仍依 `設計/交付規格與引用.md` 的 `NPC#前作編號@前作劇名` 規格。

若 component 內較早的關連劇本已明確建立兩個 provenance key 其實是同一人物、或已存在正式遷移／alias 對照，本篇必須沿用既有對照；不得再創造第三個互不相認的身份鍵。若同一人物在不同節點的姓名、傷勢、立場、死亡／生還或所知資訊會因不同 `ending_id` 分歧，本篇必須按實際前作 state 分支。

---

## 5. 多項關連：鼓勵自然形成，不作每篇配額

本規則**不要求**每次都建立多項關連。A → B 只要自洽、可運行，就是完整合法的關連設計。

但作者在 component 盤點後，必須主動問一次：

> 本篇的核心事件是否實際同時承接兩個以上既有節點的真相、後果、人物或局部世界狀態？

若答案是「是」，就應把那些節點全部列成**直接關連**，而不能為了維持單一前作格式只標一篇。

適合自然形成多項關連的情況包括：兩篇平行事件在後作匯流、一篇後傳同時處理兩個既有事件留下的不同後果、某 NPC 已在兩條枝幹分別出現而新篇真正使用兩邊建立的身份／關係、新證物同時補足兩篇各自留下的空白、兩個局部後果在地理／制度／利益上自然碰撞。

不應為了「多關連」而硬造 crossover。只有同地區、同門派、同年代、同類型案件，若彼此真相與 state 沒有實質承接，不需要建立直接關連邊。

若既有 component 已長出多個長期孤立枝幹，而新題材確實可以自然連接其中兩枝，**優先考慮建立匯流或交叉關連**，而不是習慣性再長出一條只連單一 anchor 的新葉節點。這是選題偏好，不是單篇硬性配額。

---

## 6. 最終劇本必須如何表示關連

任何觸發本模組的最終劇本，規格頭或開頭關連欄位至少要能明確列出：

- **主要關連樹**：`_任務_<根任務名>_關連樹目錄/`；
- **直接關連來源**：可為同樹或跨樹的一篇或多篇；
- 每一篇的**關連類型**：前傳／後傳／平行／承接／共享事件／其他；
- 若為跨樹關連，足以唯一辨認另一棵樹及相關任務；
- 是否為必要前置；
- 本篇 `independent`／`continuous` 的處理方式。

正文另設「關連定位」或等價段落，至少說清：

1. 本篇在世界時間與因果上位於直接來源的甚麼位置；
2. 沒有任何前作紀錄時如何開場；若本篇是合法必要前置的 `continuous` 劇本，則改寫清楚必要前置與缺少前置時不能開局的原因；
3. 會讀取哪些既有 `ending_id`／持久 state，以及每項只改變甚麼；
4. 本篇依賴哪些已由 component 建立的客觀事實；
5. 若本篇實質同時承接兩篇以上既有劇本，全部直接關連都已列出。

**不要求把整個 component 的所有節點抄進最終劇本。** 關連盤點是作者的一致性工作；最終 md 只需列本篇真正存在的主要歸檔樹、直接關連與運行所需 state。

---

## 7. 與可重覆任務的關係

若 component 中任何直接來源是可重覆任務，除本文件外，仍須同時遵守 `可重覆任務設計.md` 的 4.1「跨劇本前置隔離」。

可重覆任務不能成為另一劇本的必要前置基礎；後作不能依賴某一次 repeatable run 才成立的唯一人物、唯一真相或唯一 handoff；可以把某次 run 的結果作可選 state overlay，但必須有無該 run 的完整基線。本文件的 component 一致性不會放寬上述隔離規則。

---

## 8. 作者流程

凡創作關連劇本，流程至少加入以下步驟：

1. 選定一篇或多篇直接來源；
2. 若這是某根任務的**第一份關連任務**，建立 `_任務_<根任務名>_關連樹目錄/`，完成根任務與第一份關連任務歸檔；若來源已有關連樹目錄，沿用既有目錄；
3. 先掃描主要關連樹目錄，再以劇名、`script_id`、來源標記、反向引用及跨樹指向遞迴找出完整 component；
4. 建立作者用關連帳；
5. 先判斷哪些事實已固定、哪些仍未知、哪些只屬 branch state；
6. 再寫本篇新真相與時間線；
7. 檢查本篇是否實質承接兩篇以上節點；若是，補齊全部直接關連；若其中有其他樹，只在本篇建立跨樹指向，不合併目錄；
8. 為 `independent` 劇本寫無前作紀錄基線，再按實際 `ending_id`／state 寫可選覆蓋；
9. 完成初稿後，除一般 Phase B 外，另執行 `跨劇本關連檢查.md`。

一句話：

**單一延伸可以；第一個關連任務才建立穩定根目錄；多項關連可自然生長；跨樹只連邊不合樹；任何新節點都必須與它所屬 component 已建立的世界自洽。**
