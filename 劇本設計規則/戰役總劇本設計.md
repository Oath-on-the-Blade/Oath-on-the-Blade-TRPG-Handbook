# 劇本設計規則：戰役總劇本設計

本文件規範《武與俠》連續戰役的**戰役總劇本**如何設計與交付。

戰役總劇本不是「幾篇故事的摘要」，也不是把未完成的單篇劇本拼在一起；它是位於各階段劇本之上的**總劇本**，負責固定跨篇世界真相、跨篇因果、主要行動者、戰役級 NPC 佔位符、篇章之間的狀態接口、承接條件、反應規則與最終收束。

戰役總劇本本身**不是單桌次可直接跑團的階段劇本**，因此不以一般劇本的場景、DC、遭遇、整備、歷練等運行完整度作交付判定；但它必須完整到足以讓另一名劇本作者在不補發明跨篇因果或跨篇人物身份的情況下，依它繼續撰寫各階段劇本。

單桌實際遊玩後的世界結果不寫回 repository 內的總劇本；每一戰役階段正式結算時，由 GM 依 `GM規則/戰役存檔.md` 另外產生該桌 current `campaign_save`。總劇本負責定義「可被承接的跨篇真相、actor、戰役級 NPC key、state、ending 承接分類與階段解鎖路線」，戰役存檔負責保存「這一桌實際跑成甚麼樣、各戰役級 NPC 實際叫甚麼名字與目前是甚麼狀態，以及本次結算已正式裁定是否可繼續」。

---

## 1. 正式交付類型與檔名

正式戰役分為兩個層級：

- **戰役總劇本**：`OOTB_戰役總劇本_<戰役名>.md`
- **階段／篇章劇本**：`OOTB_戰役任務_<戰役名>(<序號>)_<篇名>.md`

戰役總劇本與階段劇本是不同交付類型。

戰役總劇本必須有穩定 `campaign_id` 與版本；階段劇本仍各自有獨立 `script_id`、版本、`replay_policy`、連續性及完整運行資料。

**階段劇本不是總劇本的章節草稿。** 每一份階段劇本都必須依一般劇本規則獨立完成、獨立結算、獨立接受一般 Phase B 與實際觸發的專項檢查。

## 2. 兩重世界真相

戰役必須同時存在兩層客觀真相，而且兩層不可互相代替。

### 2.1 跨篇世界真相

跨篇世界真相回答整個戰役的主要因果問題，包括：

- 戰役開始前已存在的根本原因與利益結構；
- 主要人物／勢力正在做甚麼、為甚麼做、掌握甚麼資源；
- 彼此之間真實的合作、利用、誤解、競爭、遮掩與利益衝突；
- 哪些事件只是局部犯案，哪些是更大結構的症狀、工具或副作用；
- 哪些關鍵問題在早期篇章只會部分暴露；
- 若玩家完全不介入，主要行動者如何沿既有利益繼續行動，以及最終會造成甚麼可預見後果。

跨篇真相必須在戰役開始時至少固定其**既存因果、人物、利益、資源、關係與當前計畫**。

但戰役不得把玩家介入後的所有未來事件寫成不可改變的固定時間線。玩家的行動會改變人物認知、資源、風險與利益，因此後續人物可以因玩家造成的新世界狀態作出新反應，形成原本尚未發生的新事件。

換言之：

> **跨篇真相固定「世界為何如此、誰正在做甚麼」；未來篇章固定「反應規則與因果邊界」，而不是固定玩家無論做甚麼都必然發生同一串劇情。**

### 2.2 篇章內任務世界真相

每一階段劇本另有自己的局部世界真相，必須完整回答該篇：

- 這次具體發生甚麼；
- 誰做了甚麼、為甚麼；
- 真實時間線與當前狀態；
- 主要 NPC 的認知、利益、計畫與下一步；
- 玩家不介入時本篇事件如何發展；
- 本篇任務成功、失敗、部分成功或放棄時如何真正結算。

**跨篇有更大的真相，不得用來降低單篇真相完整度。**

例如第一篇確認某商人確實偽造公文、盜運糧食，後續可以揭露他取得舊官紙的上游來源、其他買家或更大黑市；但不得事後改寫成「其實第一篇商人完全無責，真正幕後黑手遙控一切」，從而推翻已成立的單篇因果。

## 3. 戰役總劇本最低必備內容

戰役總劇本至少必須明列以下資料。

### 3.1 規格頭

至少包括：

- 戰役名；
- `campaign_id`；
- 總劇本版本；
- 戰役狀態：規劃中／連載中／已完結；
- 已正式發布的階段劇本；
- 當前規劃中的下一階段；
- 戰役共同起點與主要地理範圍；
- 戰役預期的角色等級／規模走向，如有；
- 共用世界知識與既有正式劇本的權威來源。

### 3.2 跨篇核心答案

必須直接寫出 GM／作者可知的核心答案，不得只寫懸念：

- 根本問題是甚麼；
- 造成問題的主要因果鏈；
- 主要受益者、執行者、利用者、受害者與誤判者；
- 哪些秘密在戰役開始時已經成立；
- 哪些事情尚未發生，只會按條件由人物反應產生。

### 3.3 跨篇真實時間線

至少列出：

- 玩家介入前已發生的關鍵事件；
- 戰役開始時各主要行動者正在執行的事情；
- 玩家不介入時的自然推進；
- 會因階段結果而改變的條件式下一步。

不得把「第二篇會發生 X、第三篇會發生 Y」當作無條件真相；若 X／Y 是人物對前篇結果的反應，必須寫明**觸發條件與行動者理由**。

### 3.4 跨篇主要行動者

每名會跨篇影響戰役的主要人物／勢力，至少要有：

- 穩定 `actor_key`；
- 身份／勢力位置；
- 初始知道甚麼、不知道甚麼、誤解甚麼；
- 核心利益；
- 當前計畫；
- 可動用資源與限制；
- 甚麼戰役狀態會令其改變計畫；
- 可預見的逃走、滅證、反查、嫁禍、倒戈、求和、搶先行動或其他反應。

`actor_key` 是戰役總劇本的**因果／機器語義鍵**，用來描述「這個行動者在跨篇結構中是誰」。若該行動者是會在可運行劇本中作為 NPC 出現的具體人物，還必須同時取得第 3.5 節的戰役級 NPC 識別鍵；`actor_key` **不得取代**正式階段劇本使用的 NPC 佔位符。

勢力、制度單位或沒有單一人物實體的行動者可以只有 `actor_key`；不要為抽象組織硬造一個 NPC key。

這些 actor 與其正常／條件式狀態亦是實際結算時核對 `campaign_save` 例外資料的基準。**作者不需要預測所有玩家能造成的例外；只需要把正常因果、可預見反應及後續會讀取的狀態寫清楚。** 玩家真正造成的意外死亡、提前被捕、倒戈、地點毀損等，由 GM 結算時記入戰役存檔，不回頭假裝總劇本早已預寫。

### 3.5 戰役級 NPC 佔位符權威列表

戰役總劇本必須持有本戰役的**唯一權威 NPC 佔位符列表**。只要一名人物會跨篇再次出現、後篇會讀取其身份／實例姓名／持續狀態，或總劇本已把他視為跨篇人物，就應登記戰役級 key。

穩定識別鍵格式：

`NPC#編號@戰役:<戰役名>`

完整姓名佔位符沿用一般姓名欄，例如：

`<NPC#7@戰役:漕河暗牒: 姓?-名?>`

列表每項至少包括：

- 戰役級 NPC 識別鍵；
- 姓名欄約束，例如 `姓?-名?`、固定姓／名或完整固定名；
- 人物身份／跨篇功能；
- 如有的 `actor_key`；
- 首次規劃登場階段；
- 首次正式登場階段／`script_id`（若已發布）；
- 若人物在制度建立前已以本地 NPC／`@前作` 出現，保存其**來源／遷移 alias**。

權威與分配規則：

1. **只有總劇本分配戰役級 NPC 編號。** 階段劇本不得自行建立 `NPC#…@戰役:<戰役名>` 後要求總綱追認。
2. 同一戰役內編號唯一且永久。已分配號碼不得因人物死亡、退出、篇章刪改或未來計畫變更而重用／重編給另一人。
3. 未正式發布的階段若新增一名確定會跨篇的人物，先更新總劇本列表，再完成／發布階段劇本。
4. 同一人物跨篇再登場時，各階段一律使用同一個 `@戰役:<戰役名>` key；不得重新編成本篇本地 `<NPC#…>`，亦不得改以「上一篇」作主識別。
5. **同一正式戰役內，戰役級 key 優先於 `NPC#前作編號@前作劇名`。** `@前作` 仍適用於不屬同一戰役的跨劇本關聯。
6. 若舊的已發布階段在本制度前已用本地 `<NPC#…>`，而該人之後才升格為跨篇人物，總劇本分配新的戰役級 key 並保存 `戰役級 key → 舊篇章 NPC 來源` 映射。舊檔可保留歷史寫法；所有之後的新篇改用戰役級 key。
7. `actor_key` 與戰役級 NPC key 的映射由總劇本維護。對具體人物應能唯一判定彼此對應；不得讓後續作者猜哪個 NPC 才是某 actor。
8. 總劇本只固定**姓名欄約束**，不保存某一桌跑出的隨機姓名。每桌實際姓名由 GM 在首次需要時實例化，並由 current `campaign_save` 保存後一路承接。
9. 若一名已登記人物在某階段不登場，該階段不必為了「湊列表」寫人物條目；但一旦引用其身份、口供、狀態或實例姓名，必須使用同一戰役級 key。
10. 總劇本改版可新增未使用 key，不得默默改變既有 key 指向的人物。需要修正錯誤時必須有明確版本遷移，不能以無痕重編破壞既有 `campaign_save`。

這份列表是**作者層身份權威**；每桌 `campaign_save` 是**運行層實值權威**。總劇本回答「這個 key 是誰／姓名可怎樣生成」，戰役存檔回答「這一桌這個 key 已實例化成甚麼名字、目前狀態如何」。

## 4. 每一階段的總劇本接口

戰役總劇本必須為每一個目前已規劃的階段提供**篇章接口**。接口不是階段劇本正文，但至少要讓下一名作者知道該篇在整個戰役中負責甚麼。

每篇至少列：

- 階段序號與暫定／正式篇名；
- 狀態：已發布／撰寫中／規劃；
- 已發布時的 `script_id` 與正式檔名；
- 本篇開始前必須帶入的 campaign state；
- 本篇會直接使用的戰役級 NPC key；
- **為甚麼現在發生**；
- **為甚麼玩家有理由／資格介入**；
- 本篇獨立任務目標；
- 本篇局部真相摘要；
- 本篇與跨篇真相接觸的部位；
- 本篇主要可改變的 campaign state；
- 本篇結束後的跨篇承接方式；
- 各主要結算結果如何映射到後續戰役狀態；
- 對每個主要 ending 明列其戰役承接分類：**可承接 → 哪一個下一篇接口**，或**提早戰役結局 → 如何在本篇收束**；
- 對每個主要 ending 明列預期戰役層結果：可承接時為 `active`；非失敗且不可承接的提前收束為 `partly_completed`；放棄或失敗且不可承接為 `failed`；原定末篇完整收束為 `completed`；
- 對每個 `partly_completed` ending，提供**玩家可見戰役收束結局**的名稱與可直接執行的收束內容／明確寫作要求：先完整收住本篇結果，再以不劇透謎面尾巴作最後一拍；
- 除第一階段外，本篇的**階段解鎖條件**：回看此前所有階段，哪些已成立因素可以解鎖本篇，以及它們如何組合。

### 4.1 階段解鎖條件必須回看此前所有階段

除第一階段以戰役共同起點／初始入口啟動外，每個後續階段都必須在總劇本內有可直接核對的**階段解鎖條件**。

總綱不得只寫「承接上一階段」。設計該階段時必須回看**此前所有已存在階段**，逐一找出真正會參與解鎖本篇的因素；沒有作用的較早階段不必硬湊，但只要第一篇、第二篇或更早結果仍是本篇入口的一部分，就必須保留來源，不得因中間多了一篇而遺失。

可作解鎖因素的資料包括但不限於：

- 某較早階段的 `ending_id`／承接分類；
- campaign state 的特定值或值域；
- 某戰役級 NPC 的存活、自由、在職、合作、逃亡、倒戈或其他持續狀態；
- 已取得／已公開／已毀／已失去的關鍵證物、物品或情報；
- 已建立的玩家資格、委託關係、敵對關係、盟友、信用、權限或資源；
- 已發生並仍然成立的世界事件、危機、制度反應或地理條件；
- 前述因素造成的具體人物反應。

每一條解鎖路線至少要寫清：

1. **來源階段**：因素最初由哪一篇建立／修改；
2. **來源因素**：具體 ending、state、人物／物品狀態、世界事實或反應；
3. **條件值**：甚麼實際值／狀態才算滿足；
4. **組合邏輯**：哪些因素必須同時成立（AND），哪些是可互相替代的路線（OR）；
5. **解鎖效果**：它如何令本篇的「為甚麼現在」與「為甚麼玩家」成立；
6. **不滿足時的結果**：本篇保持鎖定、轉由另一合法解鎖路線，或前篇分支已形成提早戰役結局。

後期階段可以由**多篇累積結果**共同解鎖。例如第四篇的入口可以同時要求第一篇取得的證據狀態、第二篇留下的 NPC／物品狀態，以及第三篇的 ending；不能把這些累積前提壓縮成「第三篇完成即可」。

反過來，如果多條不同歷史路線都能打開同一階段，總綱要分別列出它們的 OR 路線及各自帶入的差異。

**實際桌次是否可由某 ending 承接到本篇，只在該前一階段正式結算時用當時 current `campaign_save` 判定一次。** 只有當本桌當時完整前史滿足本篇至少一條完整解鎖路線，GM 才可在該次結算宣告「戰役可繼續至本篇」，並把目標階段與實際匹配路線寫入新版 `campaign_save`。之後開本篇只載入這個已結算的承接結果，不重新計算解鎖條件。

每個標為「可承接 → 本篇」的前篇 ending，都必須能對到本篇至少一條解鎖路線；若某 ending 本身不足以單獨解鎖，但與更早階段累積因素合併後可以，總綱亦必須把這個 AND 關係寫明。

總劇本不得以「詳見之後劇本」「視玩家行動而定」「GM 自行決定下一篇如何接」代替上述接口。

## 5. 非末篇的完整結算與跨篇承接

除末篇外，每一篇章任務都必須在本篇內**真正完成、失敗、部分完成或放棄並結算**。

下一篇不得靠以下方式啟動：

- 把本篇主要任務故意拖到下一篇才完成；
- 結尾突然告知「真正任務現在才開始」而否定本篇結算；
- 無因果地再收到一份新委託；
- 只以「還有幕後黑手」作抽象懸念，而沒有具體可追的問題或人物反應。

本篇結束後，跨篇推進必須由**已成立的世界因果**產生，至少採用以下一種：

### 5.1 揭露型承接

本篇已完整結算，但證物、口供、物件來源、資金流、地理痕跡、行動結果或其他已成立事實，具體暴露出一個**尚未解答的跨篇問題**。

這個問題必須具體到能指出下一階段的調查／介入方向，例如：

- 這批已廢止官紙為甚麼仍在水路流通？
- 同一枚已註銷驗角章為何在另一處出現？
- 已確認的地方犯案者從誰手上買到只有官倉內部才有的材料？

不能只寫「背後另有陰謀」。

### 5.2 反應型承接

本篇結果改變了某名人物／勢力的認知、利益、風險或資源，該人物／勢力因此採取行動，**製造出新的跨篇問題**。

例如：

- 上游供應者得知據點曝光後開始回收舊官紙；
- 被捕者的同夥搶先滅證；
- 官署為避免醜聞封存一批卷宗，反而迫使另一名知情者出逃；
- 失去貨源的買家改用更激烈方法奪取替代渠道。

反應型承接必須寫清：

- 誰收到／推知了甚麼新情報；
- 其核心利益如何受影響；
- 為甚麼選擇這個行動；
- 行動具體造成甚麼新問題；
- 為甚麼玩家會與它再次相遇。

### 5.3 兩者可同時成立

同一篇可以既留下具體未解問題，又令人物因本篇結果採取新行動。兩者同時存在時，總劇本要說明它們如何匯合，而不是變成兩條互不相干的新委託。

### 5.4 承接只屬於「可承接 ending」，並在結算一次裁定

不是每個非末篇 ending 都必須承接下一篇。總劇本必須先完成本篇結算，再判斷該 ending 是否仍有成立的下一篇接口。

- **可承接 ending**：本篇已正式結算，而且由實際 ending 留下的世界問題／人物反應、玩家介入理由、必要 state、人物、證物與資源仍足以打開下一篇；只有這類 ending 可以承接。
- **提早戰役結局**：本篇已正式結算，但該分支沒有合法下一篇接口，或已使原定後篇不應再發生；必須在本篇完成整條戰役的分支性收束。

單篇的「成功／部分成功／失敗」與戰役的「可承接／提早收束」不可混為一談。失敗可以自然製造下一篇而可承接；成功也可能提前解決核心問題而直接收束。

實際桌次的戰役層結果在該篇正式結算時一次確定：

- 可承接，且本次結算確認目標階段至少一條完整解鎖路線成立 → `active`；
- 非失敗結果、不可承接、且未跑完整個原定戰役 → `partly_completed`；
- 放棄 → `failed`；
- 失敗 ending 且不可承接 → `failed`；
- 原定完整路線跑至末篇正式收束 → `completed`。

`campaign_progress` 另記已結算階段數／本次採用總綱規劃階段數，例如 `partly_completed (2/4)`。

**放棄 ending 一律屬提早戰役結局，當前戰役在此中斷並記為 `failed`。** 世界後續仍可自行推進，但不得因世界仍有未解問題，就把已明確退出的玩家自動送進下一篇。不得用「日後重返」「之後再有人委託」作為放棄 ending 的預設承接。

對每個不可承接的非放棄 ending，總劇本必須給出正式提早戰役結局，至少固定：收束性質、戰役層狀態（`partly_completed` 或 `failed`）、已回答／未回答的核心問題、最終 campaign state、主要人物／物品狀態、`campaign_save` 後果、玩家可見戰役結局，以及原定後篇不再發生的原因。

#### 5.4.1 `partly_completed` 的玩家可見收束必須「先完成，再留謎面」

任何非失敗但不可承接、因而在未跑完整個原定戰役前以 `partly_completed` 收束的分支，必須有一個 GM 可直接執行的玩家可見戰役結局。

這個結局必須同時做到：

1. **完成感在前**：本篇主要行動、玩家取得／失去的目標、眼前危機與主要人物直接後果先明確落地。玩家應感到「這次事件已經結束」，而不是像劇本被截斷；
2. **謎面尾巴在後**：最後用一個玩家可感知、但未解的異樣、缺口、矛盾、去向、物件細節、傳聞或疑問作最後一拍；
3. **謎面不是續篇接口**：尾巴只保留世界仍有未知的感覺，不得等同下一篇已解鎖，不得變成新委託、追擊命令或「真正任務現在開始」；
4. **不劇透未公開真相**：只可使用玩家已知事實及在該 ending 中合理可見的新表象，不得直接揭露真正黑手、未公開身份或後篇答案；
5. **結算宣告**：GM 宣讀收束後，明確宣告「戰役部分完成（X/Y）」；不能只讀懸念而不交代戰役已在此收束。

**謎面尾巴是完整結局的最後一拍，不是用懸念代替結局。**

不得為了維持原定篇數而補造不存在的關鍵線索、完美備份、替代人物、委託或其他強制回線機制。

## 6. Campaign state 與篇章間接口

戰役總劇本必須定義**跨篇狀態鍵**，只保存會實際改變後續世界的資料。

每一個 state 至少要有：

- `state_key`；
- 型別／可用值；
- 首次由哪一篇建立；
- 代表的世界事實；
- 哪些後續人物／事件會讀取它；
- 它會改變甚麼開場、資源、人物態度、證據完整度、危機或後續選項。

不得建立大量只作劇情摘要、後續完全不讀取的旗標。

已發布階段劇本若已保存具體 campaign state，總劇本必須**直接採用該既有 state**；不得另造一套平行旗標描述同一結果。

若 state 指向某一個已登記的跨篇 NPC，應以戰役級 `NPC#…@戰役:<戰役名>` 或與其唯一對應的 `actor_key` 表達，不能只留下某篇局部 `<NPC#3>` 而令後篇無法穩定解析人物。

對主要結局，總劇本至少要列出：

> 前篇 ending／state → 世界狀態更新 → **承接分類** → 戰役層結果 → 若可承接：結算時驗證哪一組解鎖路線、下一篇如何開始；若不可承接：本篇如何形成 `partly_completed`／`failed` 提早戰役結局及玩家可見收束

如果多個前篇結局都可以進入同一下一篇，可以共用下一篇；但開場差異、可用證據、人物位置或風險若受前篇影響，必須在接口中明列，不能把不同結果偷偷重置成同一狀態。

實際每桌的 state 值與承接裁決不寫回此總劇本；由 `GM規則/戰役存檔.md` 在每篇正式結算後保存。總劇本只定義 key、語義、來源、讀取效果、ending 承接分類與可用解鎖路線。

## 7. 動態戰役與條件式未來

戰役總劇本應固定**反應規則**，而不是固定所有未來事件。

推薦把跨篇推進寫成：

> 已成立真相／既有利益 → 本篇事件 → 玩家結算 → campaign state 更新 → **本次結算承接性判定** → 若 active：固定下一階段及實際匹配解鎖路線 → 人物重新判斷 → 條件式反應；若不可承接：在本篇完成 `partly_completed`／`failed` 收束

對每個重要反應，至少區分：

- 觸發條件；
- 行動者知道的資訊；
- 行動者的利益；
- 行動；
- 對世界造成的可觀察變化；
- 若玩家阻止／改變該行動，戰役如何重新接回核心因果，或為甚麼應改為提早收束。

這樣可以容許玩家真正改變世界，又不把下一篇變成 GM 臨時發明。

## 8. 末篇與最終收束

末篇應是**篇章內任務真相與跨篇世界真相重疊最高的一篇**。

末篇至少應讓玩家能直接接觸並改變：

- 戰役核心因果鏈；
- 最主要行動者或其實際控制機制；
- 戰役開始時最重要的跨篇問題；
- 此前累積的 campaign state 所造成的優勢、限制、盟友、缺口或代價。

末篇仍然要有自己的完整篇章任務，而不是純粹「解說前面真相」。

戰役結束時不要求所有世界秘密百分之百公開，但必須能回答戰役的**主要問題**並處理其主要因果後果。不得把核心答案再推給不存在的下一篇。

**末篇是原定完整路線的最終收束，不代表所有桌次都必須跑到末篇。** 若較早階段的 ending 已不可承接、玩家放棄，或玩家提前真正解決核心威脅，應在該階段依第 5.4 節形成正式提早戰役結局，而不是為了抵達末篇重置世界。

可以留下：

- 次要人物下落；
- 未被證實的更遠關係；
- 不影響本戰役主要答案的世界未知；
- 可供另一個獨立戰役使用的新局勢。

但這些不能代替本戰役的收束。

---

## 9. 已發布階段、後續擴張與禁止反改

戰役可以在連載期間增加新階段、調整尚未發布的未來篇章或把原本一篇拆成多篇，但必須遵守：

- 不推翻已發布階段已成立的客觀真相；
- 不取消玩家已完成的任務結算；
- 不重置已保存的 campaign state；
- 不重編／重用已發布或已進入 `campaign_save` 的戰役級 NPC key；
- 不以後加的「真正幕後黑手」令前篇責任人突然變成無責；
- 新增篇章必須由既有真相或人物反應因果接出；
- 不把既有放棄／`partly_completed`／`failed` 提早戰役結局追溯改寫成其實一直未中斷；
- 不因總綱後續改版，在下一次開局重新計算已於前次結算裁定的承接結果；
- 若最終收束位置後移，總劇本版本必須更新，並重新通過戰役總劇本檢查。

戰役總劇本的版本更新只代表**作者層的戰役設計更新**；單桌實際遊玩結果、戰役級 NPC 的該桌實例姓名及已宣告承接裁決仍保存在該桌 `campaign_save`，不要求每跑完一篇就修改 repository 內的總劇本。

## 10. 與一般階段劇本規則的關係

### 10.1 創作戰役總劇本時

先依 `劇本設計規則/README.md` 讀取共通世界與設計規則，再完整讀取本文件。

完成總劇本初稿後，**只拿最終戰役總劇本 md**，另讀並執行：

- `劇本設計規則/戰役總劇本檢查.md`

戰役總劇本不接受一般 `檢查.md` 的「單篇可直接跑團」反大綱要求，也不需要跑 `拿手檢查.md`、`社會名譽檢查.md`、`整備檢查.md`；那些是可運行階段劇本的審查。

### 10.2 創作階段劇本時

每一份階段劇本都必須：

1. 讀取目前有效的戰役總劇本；
2. 讀取總劇本的戰役級 NPC 權威列表，對已有跨篇人物沿用原 key；若要新增跨篇人物，先回總劇本分配 key；
3. 只承接總劇本與既有 campaign state 已成立的世界事實；
4. 依一般 `設計.md` 與所有共通／觸發專項設計規則完成可直接跑團的正文；
5. 完成後回到**一般劇本 Phase B**：依序執行 `檢查.md`、`拿手檢查.md`、`社會名譽檢查.md`、`整備檢查.md`，再執行實際觸發的專項檢查。

若某桌已有前篇實際遊玩結果，運行下一篇時的 campaign state、戰役級 NPC 實例值、目標階段與承接來源，以前一階段正式結算產生的最新有效 `campaign_save` 為準；**不在新篇開局重新判定上一階段是否其實可承接。** repository 總劇本的姓名欄預設或未實例化狀態不得重置已玩出的姓名、ending、人物死亡、提前被捕、地點毀損或其他例外狀態。

**戰役總劇本檢查不得替任何階段劇本代檢。**

## 11. 戰役總劇本不是甚麼

以下文件一律不算完成的戰役總劇本：

- 只有「第一篇查案、第二篇追兇、第三篇決戰」的篇名列表；
- 只有幕後黑手、沒有跨篇因果與行動者反應；
- 只有世界真相、沒有每篇輸入／輸出 state；
- 有跨篇人物，卻沒有由總劇本統一維護的戰役級 NPC 佔位符列表；
- 每篇各自替同一跨篇人物重編 `<NPC#…>` 或只靠 `@前作` 鏈一路追來源；
- 每篇都寫「視玩家選擇調整下一篇」但沒有列條件與反應；
- 只寫「承接上一階段」，沒有記錄本篇由此前所有階段累積而來的實際解鎖條件；
- 靠延後前篇任務完成來製造連續性；
- 靠無因果的新委託串篇；
- 把放棄或其他不可承接 ending 無條件拉回下一篇；
- 把 `partly_completed` 只寫成一句「仍有更大陰謀」而沒有完整玩家可見收束；
- 把所有後續事件寫死，無論玩家做甚麼都回到相同劇情；
- 要求後續作者自行發明為甚麼下一篇現在發生；
- 把末篇只寫成「揭露真正幕後」而沒有玩家可介入的核心因果與終局。

戰役總劇本的完成標準不是篇幅，而是：**跨篇真相、人物身份、人物反應、戰役級 NPC 佔位符、篇章接口、階段解鎖條件、狀態傳遞、ending 承接分類、戰役層結果、`partly_completed` 玩家可見收束與最終／提早收束已具體到不需下一名作者替它補發明主要因果、重新辨認同一人物或臨時補一個結局。**
