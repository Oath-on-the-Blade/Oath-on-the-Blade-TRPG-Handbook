# GM規則：戰役存檔

本文件規範《武與俠》連續戰役在**每一個可獨立結算的戰役階段完成後**，如何產生、交付、保存及重新載入一份 GM 私密的 `campaign_save`。

`campaign_save` 是跨階段的**世界狀態交接檔**。它不是角色卡、不是玩家可見 `settlement_receipt`、不是進行中的 `game save`，也不是 repository 內的戰役總劇本本身。

它的目的，是讓同一桌之後續跑、換 GM、換 AI GM、換聊天或換 storage 時，只要重新提供最新有效戰役存檔，即可知道：這個戰役原本的跨篇真相與設計是甚麼、目前已完成哪些篇章、各篇達成甚麼結局、哪些 campaign state 已改變、戰役級 NPC 佔位符在這一桌已實例化成甚麼姓名，以及**上一階段結算時已正式裁定是否可繼續、若可繼續下一階段是哪一篇及依哪條解鎖路線成立**。

---

## 1. 何時必須產生，以及何時判定能否繼續

當本次正式結算的劇本屬於某一連續戰役階段，即符合以下任一情況時，結算必須額外產生 `campaign_save`：

- 正式檔名為 `OOTB_戰役任務_<戰役名>(<序號>)_<篇名>.md`；
- 規格頭明列 `campaign_id`／戰役線並宣告本篇會建立或讀取 campaign state；
- 戰役總劇本把本篇列為其正式階段。

**第一篇亦要產生。** 不因沒有前篇可承接而省略。

只要該階段已進入正式結算，無論結果是完成、部分完成、失敗或任務放棄，都要產生戰役存檔。戰役存檔記錄「實際發生了甚麼」，不是只保存成功路線。

若某段只是同一未結算劇本內的幕間、場景或 session 切點，不另產生戰役存檔；只有該篇章本身按劇本規格正式結算並關閉 `game_id` 時才產生。

**戰役能否進下一階段，只在本篇正式結算時判定一次。** GM 於本次結算讀取本次採用的戰役總劇本、當前 ending、此前全部有效 `campaign_save` 世界狀態與本篇凍結結果，判定：

1. 本 ending 是否在總綱標為可承接；
2. 若可承接，實際前史是否完整滿足目標階段至少一條總綱已定義的 AND／OR 解鎖路線；
3. 若成立，下一階段是哪一篇，以及本桌實際匹配哪一條路線；
4. 若不成立，這一桌戰役應以 `partly_completed`、`failed` 或 `completed` 哪一種狀態正式收束。

這個裁決會寫入本次 current `campaign_save`，並在同一次結算向玩家宣告。**之後開下一篇時不得重新計算這次承接，也不得因 repository 總綱後續改版追溯改判已宣告的戰役結果。**

戰役存檔把「**目前跑了多少篇**」與「**當前戰役是否仍可承接**」分開記錄：

- **仍可承接**：`campaign_status=active`。例如已正式結算 2 篇、目前採用總綱規劃 4 篇，記 `campaign_progress=2/4`、`continuation_status=open`。本篇即使是失敗 ending，只要仍屬可承接並在本次結算確認下一階段完整解鎖路線成立，仍是 `active`；
- **未跑完全部規劃階段，但以非失敗結果正式提早收束**：`campaign_status=partly_completed`。例如 `campaign_progress=2/4`、`continuation_status=closed`；
- **放棄，或失敗 ending 且不可承接**：`campaign_status=failed`。例如 `campaign_progress=2/4`、`continuation_status=closed`；
- **原定完整路線已跑至末篇正式收束**：`campaign_status=completed`。例如 `campaign_progress=4/4`、`continuation_status=closed`。

`partly_completed`、`failed`、`completed` 都是**正式關閉當前戰役鏈**的結果，不是暫停狀態。世界後果仍可存在，但不能因此自動開原戰役後篇。

## 2. 私密性、玩家提示與下載交付

`campaign_save` **內含 GM 私密資料及未公開跨篇劇透**，包括戰役總劇本快照、未揭露真相、後續行動者資料、該桌已實例化但玩家未必知道的 NPC 姓名，以及可能尚未被玩家知道的 campaign state。

因此它與玩家可見 `settlement_receipt` 分開處理。

AI GM／GM 在提供下載前，必須明確提示玩家：

> **這是一份 GM 私密戰役存檔，內含未公開真相及後續劇透。請下載保存，但不要打開或閱讀；下次繼續本戰役時，直接把原檔交給／上傳給 GM 或 AI GM。**

最低交付要求：

- 產生一份可重新下載／重新上傳的完整檔案；
- 由 host 或指定保管者至少可取得；不要求每名玩家都下載一份；
- 若 storage 支援權限，持久副本應保存在 GM 私密位置；玩家端下載副本只作封存／轉交，不因此取得閱讀授權；
- 不得把 `campaign_save` 的正文貼入公共聊天、玩家可見 `settlement_receipt` 或角色卡；
- 玩家可見結算只需說明「已產生 GM 私密戰役存檔」及其下載狀態，不摘要其中劇透。

玩家若不慎打開，GM 不用改寫世界真相來補救；按桌面共識處理劇透即可。規則責任仍是**在交付前清楚標示私密性**。

## 3. 檔名、識別與版本

正式 Markdown 檔名使用：

`OOTB_戰役存檔_<戰役名>_截至(<序號>)_<篇名>_v<campaign_save_version>.md`

例如：

`OOTB_戰役存檔_漕河暗牒_截至(1)_河倉三封急牒_v1.md`

每一桌實際戰役另有穩定：

- `campaign_save_id`：第一次產生戰役存檔時建立，之後同一桌整個戰役沿用；
- `campaign_id`：引用戰役總劇本的正式 ID；
- `campaign_save_version`：每次正式產生新版存檔時遞增。

正常完成下一階段會產生新版；若結算校正改變任何戰役狀態、階段 ending、戰役級 NPC 實值／映射、關鍵人物狀態或其他 `campaign_save` 內容，亦須遞增版本。不得無痕覆寫舊檔。

舊版可保留作稽核，但必須標記 `superseded`；只有一份可標記為 `current`。

---

## 4. 戰役存檔最低必備內容

每份 `campaign_save` 必須可由另一名 GM **單獨讀取**並還原目前跨篇狀態，不得要求其回想舊聊天。

### 4.1 存檔規格頭

至少包括：

- `campaign_save_id`；
- `campaign_save_version`；
- `campaign_id`；
- 戰役名稱；
- `campaign_status: active | partly_completed | failed | completed`；
- `campaign_progress: <已正式結算階段數>/<本次採用總綱目前規劃階段數>`，例如 `2/4`；
- `continuation_status: open | closed`；
- `campaign_status_reason: active_continuation | early_campaign_ending | abandoned | failed_noncontinuable | final_stage`；
- 目前已結算至第幾篇及篇名；
- 最新階段 `game_id`、`script_id`、劇本版本；
- 最新有效 `receipt_version`；
- 結算日期／時間及遊戲內結束時點；
- Handbook 版本／來源；
- 本檔狀態：`current | superseded`。

合法組合固定為：

- `active` → `continuation_status=open`；
- `partly_completed` → `continuation_status=closed`；
- `failed` → `continuation_status=closed`；
- `completed` → `continuation_status=closed`。

`campaign_status_reason` 只描述戰役層結果，不取代本篇 `ending_id`、單篇結算類型或玩家可見結局名稱。`campaign_progress` 的分母以**本次存檔採用的總綱快照**為準；日後作者擴張尚未遊玩的戰役時，不回頭無痕改寫舊存檔的歷史分母。

### 4.2 戰役總劇本快照

必須同時保存：

- 戰役總劇本名稱；
- `campaign_id`；
- 總劇本版本；
- 正式檔名；
- repository 路徑或可用連結；
- **本次結算時實際採用的完整戰役總劇本快照**。

不能只留一條日後可能失效或內容已更新的 URL。連結用於尋找來源；內嵌快照用於證明當時真正採用哪一版跨篇真相、戰役級 NPC registry、ending 承接分類與篇章解鎖接口。

若 repository 之後更新總劇本，舊戰役存檔中的快照不被倒寫。上一階段已在結算宣告的承接結果亦不因 repository 後續更新而重算。

### 4.3 戰役階段履歷

由第一篇至目前篇，逐篇列出：

- 階段序號與劇本名稱；
- `script_id`、劇本版本；
- 正式檔名；
- repository 路徑或可用連結；
- 該篇 `game_id`；
- 最終 `receipt_version`；
- 結算類型；
- `ending_id`；
- 玩家可見結局名稱；
- 遊戲內結束時點；
- 該篇是否已正式關閉。

**不得只記「第一篇完成、第二篇完成」。** 必須能知道每一階段實際達成哪個 ending。

未正式發布／未遊玩的未來篇章可以只由戰役總劇本快照保存，不得在「已完成階段履歷」內偽裝成已結算。

### 4.4 目前 campaign state

把戰役總劇本及各已發布階段定義、且後續仍會讀取的 campaign state 保存為目前有效值。

每項至少包括：

- `state_key`；
- 目前值；
- 最後由哪一篇／哪個 ending／哪次結算建立或修改；
- 它代表的世界事實；
- 若該值含 GM 私密資訊，保持在本私密檔內，不同步到玩家憑證。

已由前篇正式建立的 state 必須沿用原 key，不另造同義平行旗標。

### 4.5 戰役級 NPC 實例映射與關鍵人物／地點／證物目前狀態

#### A. 戰役級 NPC 實例映射

戰役總劇本是 `NPC#編號@戰役:<戰役名>` 的**作者層權威列表**；本 `campaign_save` 是這一桌對同一批 key 的**運行層實值權威**。

凡某個戰役級 NPC 已在本桌任何已結算／進行過的階段中實際需要姓名、已被 GM 實例化，或由舊篇本地 NPC 遷移成戰役級 key，都必須保存一筆映射。每筆至少包括：

- `campaign_npc_key`：例如 `NPC#7@戰役:漕河暗牒`；
- 總劇本姓名欄約束，例如 `姓?-名?`、`何-名?`、固定全名；
- `actor_key`（如有）；
- `realized_name`：這一桌已生成／已固定的實際姓名；
- `realization_status: instantiated | fixed_by_master | migrated_from_legacy`；
- 首次實際出現／實例化的階段、`script_id` 與 `game_id`；
- 玩家是否已知其姓名／顯示稱呼（若流程需要）；
- 若由制度建立前的舊篇本地 NPC 承接，保存 `legacy_source`，例如 `<NPC#3@河倉三封急牒: 姓?-名?>`；
- 最後一次核對來源。

硬規則：

1. **同一 `campaign_npc_key` 一旦在這一桌有 `realized_name`，後篇不得重新生成姓名。** 換 GM、換 AI、換聊天、總劇本版本更新都不能令它改名。
2. 兩個不同戰役級 key 不得因讀檔失誤被合併成同一人物；同一人物亦不得在後篇被拆成兩個新 key。
3. 總劇本未來篇章中的未登場 NPC 可以尚無 `realized_name`；不要為了填表預先替未見人物抽名。其姓名約束已存在於內嵌總劇本 registry 即足夠。
4. 若某一已發布舊篇在戰役級 key 制度前只使用本地 `<NPC#…>`，而總劇本已建立遷移 alias，結算時要把**該桌舊 NPC 已實例化的姓名**搬入對應 `campaign_npc_key`，標記 `migrated_from_legacy`，不得重新抽一個新名字。
5. 若總劇本姓名欄是固定全名，`realized_name` 必須與之相符；若是可變欄位，存檔保存這一桌實際生成值，不把它回寫成 repository 官方姓名。
6. 若存檔顯示某 key 已實例化，而當前 stage／GM 仍試圖生成另一名字，視為讀檔衝突，停止使用新名字並以 current `campaign_save` 為準。

#### B. 關鍵人物目前狀態

對戰役總劇本列為跨篇主要行動者、或已發布階段明列會影響後篇的關鍵 NPC，保存目前實際持續狀態。

人物優先使用：

- `campaign_npc_key`（若已列入總劇本 registry）；
- 對應 `actor_key`（如有）；
- 已發布舊篇的 `legacy_source`／本地 NPC 來源（只作 provenance）；
- 目前狀態，例如在場、自由、被捕、合作、失蹤、逃亡、重傷、死亡、職位改變等。

**同一戰役人物若已有 `campaign_npc_key`，不得再以 `<NPC#前作編號@前作劇名>` 當主鍵另存一份平行人物狀態。** 舊來源只附在同一筆記錄內。

#### C. 關鍵地點／證物目前狀態

地點／證物保存其穩定識別及目前狀態，例如完好、燒毀、封存、失落、被某方持有等。

角色卡仍是 PC 自身數值、裝備與成長的權威；戰役存檔只在某個 PC 與世界的特定關係本身會影響跨篇因果時，才記錄必要的角色識別與該世界關係，不重複整張角色卡。

### 4.6 例外資料

必須明列：

- `exception_status: none | present`

若為 `present`，逐項建立例外紀錄。最低欄位：

- `exception_id`；
- 受影響對象：優先 `campaign_npc_key`／`actor_key`，或地點／證物識別；舊篇本地 NPC 來源只作補充 provenance；
- **劇本／總劇本原本預期或正常可推導的狀態**；
- **實際狀態**；
- 造成例外的玩家行動、NPC 行動或世界事件；
- 例外成立的來源：凍結 save、場景紀錄、ending／settlement record 等；
- 對後續戰役的直接影響；
- 下一名 GM 必須保留的限制或承接要求。

典型例外包括但不限於：

- 劇本沒有預期會死亡的關鍵 NPC 被玩家殺死或意外死亡；
- 預定逃脫者反而被玩家提前活捉；
- 預定被捕者被玩家放走、救走或招攬；
- 關鍵 NPC 永久重傷、失去職位、倒戈或成為玩家盟友；
- 跨篇重要地點提前被燒毀、淹沒、查封或由另一方控制；
- 關鍵證物被玩家帶走、毀掉、公開或交給原本未預期的勢力；
- 玩家以合理方法提前突破戰役總劇本預設的承接條件。

若沒有任何例外，必須寫 `exception_status: none`，不能用空白表示「沒有」或「忘了檢查」。

**例外不等於錯誤。** 玩家合理造成的預期外結果必須被保存；它可以令另一條合法承接路線成立，也可以令當前戰役在本篇正式部分完成／失敗收束，不能因不方便而重置回劇本預設。

### 4.7 本次結算的承接裁決／戰役收束

本節是**本次結算已正式裁定的結果**，不是留給下一次開局重新判斷的備忘。

若 `campaign_status=active` 且 `continuation_status=open`，至少保存：

- `continuation_decision: continue`；
- 目標下一階段的序號及正式／暫定名稱；
- 最新 ending 在總綱中的「可承接 → 目標階段」映射；
- 目標階段總綱接口中的階段解鎖條件；
- **本次結算實際匹配的完整解鎖路線**：逐項列出來源階段、來源 ending／state／人物／物品／情報／玩家資格／世界事件／人物反應、規則要求值與本桌實際值；
- 若有多項 AND 條件，逐項確認全部已滿足；若有多條 OR 路線，明列本桌實際匹配哪一條／哪些完整路線；
- 會直接讀取的 campaign state；
- 下一篇直接使用的戰役級 NPC key，以及其中哪些已在本桌有 `realized_name`；
- 若屬世界內直接連續，保存合法 `continuity_handoff` 的短期資源／狀態；
- 已知會因例外資料而改變的開場條件；
- 本次已向玩家宣告「戰役可繼續」的紀錄，以及可公開的下一階段名稱／提示（若劇本允許公開）。

**不得只因上一階段已結算便判可繼續。** 若 ending 標為可承接，但以本次結算完整前史無法滿足目標階段任何一條完整解鎖路線，這是總綱／結算的一致性錯誤：本次戰役存檔驗證失敗並維持 `settling`，先在遊戲階段外修正正式來源，不得猜測補條件或直接把戰役標為 active。

若 `continuation_status=closed`，至少保存：

- `continuation_decision: stop`；
- 終止於哪一篇／哪個 ending；
- `campaign_status`、`campaign_progress`、`campaign_status_reason`；
- 對應的完整／部分／失敗收束；
- 主要人物、證物、世界與 campaign state 最終狀態；
- 玩家可見戰役結局名稱；
- 本次 GM 實際宣讀的玩家可見戰役收束文本或其穩定引用；
- 本次已向玩家宣告的戰役結果，例如「戰役部分完成（2/4）」或「戰役失敗（2/4）」；
- `next_stage: none`／「無下一階段交接」。

其中 `campaign_status=partly_completed` 的玩家可見戰役收束必須：

1. **先有完成感**：先把本篇主要行動、玩家實際取得／失去的目標、眼前危機與主要人物直接後果收完整；
2. **最後才留謎面尾巴**：用一個玩家可見但未解的異樣、缺口、矛盾、去向、物件細節、傳聞或疑問作最後一拍；
3. **謎面不等於承接**：尾巴不能變成新委託、追擊命令、「真正任務現在開始」或任何自動解鎖下一篇的訊號；
4. **不揭 GM 真相**：只能使用玩家已知或在本 ending 中合理可見的表象，不得直接曝光未公開真正黑手、身份或後篇答案。

**謎面尾巴是完整結局的最後一拍，不是用懸念代替結局。**

此節不得自行替尚未完成的下一篇發明新真相；只整理已在本次採用總綱、已發布劇本及實際結算中成立的資料。

---

## 5. 生成來源與禁止補腦

生成 `campaign_save` 時，只可使用：

- 本次結算凍結的最後有效 `game save`；
- 本次階段劇本最終 md；
- 本次採用的戰役總劇本；
- 已正式完成的前篇戰役存檔；
- `settlement_record`／最新有效 `settlement_receipt`；
- 本次結算已核對成立的世界狀態。

不得從作者聊天、未發布草稿、GM 腦內安排或「原本打算如此」補入實際世界狀態。

若某個**會實際影響本次承接裁決或後續**的關鍵人物、地點、證物、campaign state 或已實例化的戰役級 NPC 姓名在上述來源中無法判定：

- 不得猜測；
- 先回查上一版 current `campaign_save`、本局凍結 save 與劇本已寫明的不介入／偏離結果；
- 若是舊篇 NPC 遷移，依總劇本 registry 的 `legacy_source` 找回同一桌既有實值；
- 若仍無法唯一判定，戰役存檔驗證失敗，本次結算維持 `settling`；
- 需要在遊戲階段外依正式劇本／存檔校正後，才可完成戰役存檔並關閉。

尚未在本桌登場、亦從未需要姓名的未來戰役 NPC **不屬缺失實值**；不得為通過檢查而預先生成。

不影響後續的普通背景 NPC 不要求逐一追蹤。

## 6. 生成、NPC 實例合併、承接分類與玩家宣告流程

正式生成時依序：

1. 載入上一版 `campaign_save`；第一篇則建立新的 `campaign_save_id`；
2. 載入**本次結算實際採用**的戰役總劇本完整快照及其戰役級 NPC registry；
3. 驗證上一版已保存的 `campaign_npc_key` 在本次採用總劇本仍指向同一人物；若 key 被重編／重用，停止結算並處理版本相容性；
4. 把本篇結算結果追加到階段履歷；
5. 依本篇 ending 與實際世界結果更新 campaign state；
6. 合併戰役級 NPC 實例映射：既有 key 的 `realized_name` 原樣保留；本篇首次實例化者由凍結 save 取得；舊篇遷移者依 `legacy_source` 搬入既有姓名；未登場未實例化者不生成；
7. 逐一核對跨篇主要行動者與後續相關 NPC／地點／證物的實際狀態；
8. 比較總劇本／階段劇本原本正常狀態與本局實際狀態，建立 `exception_status` 及例外紀錄；
9. 讀取總綱對本篇 `ending_id` 的戰役承接分類及本篇正式結算類型；
10. 若 ending 標為「可承接 → 目標階段」，**就在本次結算**以本桌完整前史逐項驗證目標階段總綱接口的 AND／OR 解鎖條件；只有至少一條完整路線成立時，才設 `campaign_status=active`、`continuation_status=open`、`campaign_status_reason=active_continuation`，並整理第 4.7 節實際匹配路線與下一篇交接。**本篇即使結算類型為失敗，只要這一步成立，仍是 active，不標 failed**；
11. 若 ending 被標為可承接但本次結算沒有任何完整解鎖路線成立，停止生成完成態存檔，本次結算維持 `settling`；不得自行把 ending 改成不可承接，也不得補造解鎖因素；
12. 若 ending 不可承接／屬提早戰役結局：
   - 放棄 ending → `campaign_status=failed`、`continuation_status=closed`、`campaign_status_reason=abandoned`；
   - 正式結算類型為失敗 → `campaign_status=failed`、`continuation_status=closed`、`campaign_status_reason=failed_noncontinuable`；
   - 其他非失敗的提早正式收束 → `campaign_status=partly_completed`、`continuation_status=closed`、`campaign_status_reason=early_campaign_ending`；
13. 若本篇是本次採用總綱的末篇並完成正式最終收束 → `campaign_status=completed`、`continuation_status=closed`、`campaign_status_reason=final_stage`；末篇若劇本本身另有正式失敗／放棄結果，仍按該 ending 的正式戰役收束定義及上述失敗規則記錄，不以「到了末篇」強行改成成功完成；
14. 依已正式結算階段數與本次採用總綱目前規劃階段數寫入 `campaign_progress`；
15. 依第 4.7 節寫入**本次最終承接裁決**：active 時固定下一階段與實際匹配解鎖路線；closed 時固定「無下一階段」及玩家可見戰役收束；
16. 遞增 `campaign_save_version`；
17. 寫出完整 Markdown；
18. **重新開啟並完整讀取**該下載檔，確認階段履歷、ending、campaign status／progress／continuation、state、戰役 NPC key→實值映射、人物狀態、例外、總劇本快照，以及 active 時的目標下一階段與本次實際匹配解鎖路線都存在且一致；
19. 在同一次結算向玩家宣告戰役結果：
   - `active`：明確宣告「本戰役可繼續」，並按劇本允許提供不劇透的下一階段名稱／提示；
   - `partly_completed`：先宣讀第 4.7 節的完整玩家可見收束，再宣告「戰役部分完成（X/Y）」；
   - `failed`：宣讀相應失敗／放棄收束，並宣告「戰役失敗（X/Y）」；
   - `completed`：宣讀最終戰役結局，並宣告「戰役完成（X/Y）」；
20. 記錄上述玩家宣告已完成，標記新檔為 `current`，舊版為 `superseded`。

不能只把本篇差異 append 到舊檔而不重新輸出完整目前狀態。**每一版 current 戰役存檔都必須是可獨立交接的完整快照。**

對戰役級 NPC 尤其要檢查：

- 已實例化 key 沒有掉失；
- 已實例化姓名沒有被重新生成；
- `actor_key`／legacy source 沒有錯接到另一人；
- 已死亡、失蹤、被捕等狀態沒有因新篇預設而回復；
- 玩家尚未知道的姓名可以保持 GM 私密，但實值本身仍須保存。

## 7. 與結算憑證及 delivery manifest 的關係

`settlement_receipt` 是玩家可見的本局結算證明；`campaign_save` 是 GM 私密的跨篇世界交接。兩者不得混為一份。

戰役階段結算的 `delivery_manifest` 必須額外列出目前有效 `campaign_save`：

- 穩定檔案識別／路徑；
- 檔名；
- 格式；
- `campaign_save_id`／`campaign_save_version`；
- 閱聽範圍：`GM 私密；玩家只保管、不開啟`；
- 持久保存位置；
- 玩家／host 下載交付方式；
- `available_unconfirmed | download_confirmed | failed`；
- 後端提供時的內容校驗值。

只要戰役存檔屬本次必需交付，而其交付狀態仍是 `failed`、不能重新讀取、缺少必要欄位、缺少已實例化戰役 NPC 的實值映射、缺少本次承接／收束裁決，或沒有提供可下載／轉交的完整檔案，本次戰役階段結算不得關閉。這裡的 delivery `failed` 是**檔案交付失敗**，與 `campaign_status=failed` 的戰役結果不同。

---

## 8. 下一階段如何載入已裁定的承接結果

下一個戰役階段開始時，host／指定保管者把**上一階段結算產生的最新 current 戰役存檔原檔**交給 GM／AI GM；玩家不需要先打開或整理內容。

本節只負責**載入上一輪結算已經作出的承接裁決**，不重新判定能否繼續。

GM 在建立新 `game_id` 前／準備新階段主持資料時：

1. 讀取 `campaign_save`，確認檔案可完整讀取且為 `current`；
2. 讀取 `campaign_save_id`、`campaign_id`、版本、`campaign_status`、`campaign_progress`、`continuation_status`、`campaign_status_reason` 與上一階段 ending；
3. 若 `continuation_status=closed`，或 `campaign_status` 為 `partly_completed | failed | completed`，該存檔沒有下一階段交接；不得用它開原戰役後篇；
4. 若 `campaign_status=active` 且 `continuation_status=open`，直接讀取**上一階段結算已固定**的目標下一階段、實際匹配解鎖路線、campaign state、NPC 實值／狀態、證物／物品／情報、世界事件、例外與 `continuity_handoff`；
5. 確認本次準備運行的劇本就是存檔指定的目標階段；這是交接識別核對，不是重新評估解鎖條件；
6. 對當前階段引用的既有戰役 NPC，先套用存檔實際姓名與狀態，禁止重新生成姓名；只有從未實例化而在本階段首次需要姓名的 key 才按本次交接採用的總綱姓名欄約束生成；
7. 以本桌已成立世界事實作為本局起點，不得被 repository 預設起點重置；
8. **不得在此重新計算上一階段 AND／OR 解鎖條件、不得用新版總綱改判上一輪已宣告的 `active/closed`、不得把 `partly_completed`／`failed` 變回 active。**

若 repository 在兩次遊玩之間更新，而新版總綱／階段劇本與 current `campaign_save` 已裁定的承接、人物 identity 或世界事實衝突，應在遊戲階段外另作版本相容性處理；在完成正式遷移前，以 current `campaign_save` 內嵌的當時總綱快照與已宣告承接結果為本桌歷史權威。**版本相容性處理不得變成重新投票是否其實能承接。**

## 9. 校正、保存與清理

若之後發現正式結算有可核對錯誤，且校正會改變以下任一項：

- 階段 `ending_id`／結算類型；
- `campaign_status`／`campaign_progress`／`continuation_status`／`campaign_status_reason`；
- 本次結算裁定的目標下一階段／實際匹配解鎖路線；
- campaign state；
- 戰役級 NPC key 的實值／遷移映射；
- 關鍵人物／地點／證物狀態；
- 例外資料；
- 玩家可見戰役收束／結果宣告；

則必須回到**原結算校正流程**，以正式來源重新核對該次結算，另外產生新版 `campaign_save`，遞增 `campaign_save_version`，並在檔內記錄校正來源與被 supersede 的版本。**不能在下一次開局以「重新檢查」無痕改判。**

只改變角色個人升級選擇而不影響任何跨篇世界資料時，不要求重發戰役存檔。

正式清理 `game save` 時，**不得清除最新 current `campaign_save`**。它與正式 `settlement_receipt` 一樣屬結算後持久交付物，但閱讀權限不同。

戰役完結後，最後一份 `campaign_save` 仍保留，作該桌整個戰役的 GM 私密世界紀錄；不得因沒有下一篇便刪除。
