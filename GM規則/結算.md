# GM規則：結算

本文件是《武與俠》劇本結算的權威程序。它處理完成、失敗、任務放棄或提前撤離後的結局確認、參與資格、得失、歷練與升級、俠名／惡名／名氣／相對名譽、長期特殊傷患、江湖履歷、結算憑證、角色卡寫回觸發、**結算後角色卡更新窗口**及存檔關閉。

- 遊戲如何到達終局及如何把凍結存檔交入結算，見 `GM規則/遊戲流程.md`。
- 角色卡欄位與江湖履歷格式，見 `GM規則/角色卡格式.md`。
- **既有角色卡的實際更新 transaction、重新驗證與完整卡交付，統一見 `GM規則/角色卡更新.md`。**
- 歷練、升級、外功點數及其他角色機械數值，以 `遊玩規則/` 為準；社會名譽公式見 `遊玩規則/角色/社會名譽與門派.md`，正式相對名譽對象見 `內容庫/相對名譽對象.md`。

`game_id`、`receipt_version`、`settlement_record` 等識別只屬 GM／系統結算稽核或結算憑證。**玩家角色卡不抄寫 `game_id`、`receipt_version`、`pending_advancement`、`pending_class` 等英文／機器欄位。**角色卡只寫實際角色結果及中文「待處理更新：必須處理／容後處理」。

---

## 1. 結算階段與權限邊界

一份劇本流程正式停止接受新遊戲行動後，狀態依序為：

1. `settlement_pending`：終局事實及最後有效 `save_version` 已凍結，等待宿主／系統切換階段；
2. `settling`：宿主／系統已開啟結算階段，依本文件計算、核對、寫回並提供結算後角色卡更新窗口；
3. `closed`：角色卡、江湖履歷與正式憑證均已生成完整可下載檔案、向相關玩家開放並重新讀取驗證，結算後更新窗口已提供，進行中存檔已按第 10 節關閉或清理。

玩家確認結局、放棄任務或完成最後行動，只能令遊戲進入 `settlement_pending`；普通玩家訊息不能自行擴張 persistent storage 權限。必須由宿主／系統級流程作出明確階段切換，AI GM 才能進入 `settling`。

在 `settling` 中，只可讀取：

- 本 `game_id` 的最後有效 game save 與結算工作紀錄；
- 本次劇本及完成結算所需的正式規則；
- 與本 `game_id` 明確綁定、列入參與紀錄的 PC 角色卡。

不得順便搜尋、瀏覽、整理或更新其他角色卡、其他 `game_id`、戰役級索引、玩家級紀錄、Drive 資料夾、資料庫或任何無關 persistent storage。所有需要跨劇本保留的玩家可見角色後果，應寫入本局角色卡；宿主另有長期索引同步需求時，須在本結算階段外處理。

`settlement_record` 是依凍結存檔建立的權威工作紀錄，可以包含結算所需但不應公開的 GM 資訊。`settlement_receipt` 是從同一來源抽出的玩家可見憑證，只保存已公開結果、實際得失、參與資格、角色卡增減與核對資料；兩者不得混用而洩露隱藏真相。

## 2. 凍結來源與確認結局

開始計算前，先保存並鎖定：

- `game_id`、最後有效 `save_version` 與凍結時間；
- `script_id`、劇本名稱、版本／來源；
- 本局有效 `replay_policy`、`continuity_mode`；
- 實際使用的 Handbook 版本、release、tag 或 commit SHA；
- 終局時的 PC、NPC、劇情、危機、物品、社會名譽、其他關係與世界狀態。

凍結後不再接受會改動本局結果的新遊戲行動。若玩家只是補充可由既有存檔核對的抄寫或計算錯誤，依第 9 節處理；不得以結算核對重開已完成的行動申辯。

按已成立的世界狀態確認：

- **結算類型**：完成結局、失敗結局、任務放棄或提前撤離；
- **實際結局**：劇本內穩定 `ending_id`、玩家可見名稱及重要變體；
- **結束時點**：現實結算日期及可靠的遊戲內日期／時點；
- **直接世界後果**：只依已成立因果，不為方便結算改寫劇本真相。

不得把失敗、任務放棄或提前撤離寫成「完成」。若玩家造成劇本未預寫但因果成立的新結局，使用 `derived:<簡短識別>`，另給不劇透的玩家可見名稱，並保存所參照的最近預寫結局及推導依據。

玩家嚴重偏離劇本並確認放棄任務時，依 `GM規則/遊戲流程.md` 的任務邊界程序停止生成劇本外內容，再以「任務放棄／提前撤離」進入本文件。劇本有明列的放棄／撤離結局時照其內容；沒有時不得套用最接近的完整結局歷練，也不得為了產生獎勵而延伸另一場即興冒險。

## 3. 參與紀錄與結算資格

為每名曾綁定本 `game_id` 的 PC 建立 `participation_record`，至少記錄：

- 進入及離開核心事件的場景／時點；
- 全程參與、中途加入、中途離開或替補加入；
- 死亡、失蹤、被俘、永久留置或退休等令參與終止的世界內原因；
- 劇本明列的完整／局部參與條件及實際符合情況。

結算資格遵守：

- 短暫離線、休息或其他沒有令角色退出核心事件的 OOC 中斷，不會單獨削減資格；
- 全額結局歷練只適用於實際符合該結局參與條件的 PC，不能只因角色卡曾綁定本局、玩家短暫出現或角色趕上最後一幕便取得；
- 中途加入或離開者先用劇本明列的個人參與、早退或局部結算規則；劇本未明列時，只按該角色實際經歷的核心事件、風險、決策與持續後果推導**個人基礎歷練**；
- 個人基礎歷練的 tag／點數不得超過本局完整結局的基礎總歷練，也不得加入該角色未實際經歷的 tag；確定個人基礎歷練後，才作角色等級折算及正式個人加成；
- 完全沒有實質介入核心事件者的個人基礎歷練可為 0，但仍如實記錄其參與及結束狀態；
- 角色因本局核心衝突而死亡、被俘、失蹤、永久留置或退休，不會只因結果不利而失去已實際取得的歷練；物品、報酬及可用狀態仍按世界內實際結果處理；
- 替補 PC 是另一名角色，分開計算加入後的經歷；不得轉移離場或死亡 PC 的歷練、物品、履歷或資格。

不得只用實際遊玩分鐘數、玩家發言次數、擊殺數、最後一擊或 GM 對「貢獻度」的印象分配歷練。資格有疑義時，引用劇本條件與已保存事件，不臨場獎懲玩家。

## 4. 物質得失、應收項目與共有財產

結局章列出「獎勵」不等於物品自動出現在角色卡。所有銀兩、物品、秘笈、證物、坐騎、通行權或其他可轉移利益，依終局時的實際控制、交付及所有權分類：

- **實際取得**：已由指定 PC 或全隊合法收取、帶走或控制，才寫入相應角色卡；
- **應收未收**：報酬、欠款或承諾已成立但尚未交付，只記債權／承諾及欠付者、內容、領取條件與期限，不先增加銀兩或物品；
- **暫時保管／借用**：記錄真正所有者、保管者、可用範圍與歸還條件，不改寫成永久私產；
- **共同持有／尚未分配**：在 GM／結算紀錄建立穩定 `shared_asset_id`；角色卡只以中文「共有資產識別」引用同一項目，並記共同權利人、目前保管者／位置及使用限制，不當成每名 PC 各有一份；
- **未取得／失落／留置／毀損**：不加入角色資產，只按需要記錄去向與世界後果。

可分配的共同銀兩與物品由玩家決定分配。GM 只確認可分配的實際總量、所有權限制與既有承諾，不得擅自平均、抽籤或指定主人。玩家未達共識時保持共同持有；角色死亡、離席或替補加入也不會令財產自動轉移，繼承、交還、侵佔或贈與必須有世界事件或權利依據。

同一共有項目若需在多張角色卡保存，所有角色卡使用相同「共有資產識別」、實際總量、保管狀態與共同權利，不複製數量或機械效果。所有個人及共有得失都須列入 `settlement_record` 與玩家可見憑證。

## 5. 長期特殊傷患的角色卡紀錄

劇本造成的經脈損傷、內傷、毒傷、舊患、修練反噬或心理創傷，若被劇本正式定義為「長期特殊傷患」，必須在本次結算指定寫入角色卡的「長期狀態／特殊傷患」欄並跨劇本保留；實際寫回程序依 `GM規則/角色卡更新.md`。

角色卡每項至少記錄：

- 傷患名稱；
- 具體機械效果；
- 何時觸發或惡化；
- 對行動／武學／修練的限制；
- 治療或解除條件；
- **玩家可辨識來源**，例如劇本名稱、結局或造成傷患的事件。

供 GM 稽核的來源 `game_id`、結算憑證版本等只保存在 `settlement_record`／`settlement_receipt` 或後端紀錄，不抄進角色卡。

換劇本、結算、休息一次或單純升級不會自動清除長期特殊傷患；只有達成其正式解除條件才移除或版本化更新。它必須有符合《武與俠》世界觀的醫理、毒理、心理或武學成因，不得以沒有規則依據的超自然詛咒取代。

普通短期氣血耗損、氣血骰、功力、武勢、場景狀態、臨時毒性或戰鬥標記，不得因結算而自動變成長期傷患。若下一段採 `continuous`，所需短期狀態只留在同一 game save 或正式 `continuity_handoff`；採 `independent` 時不帶入，但已消耗／失去的物品及真正持續的後果仍保留。

角色死亡、退休、失蹤、被俘或永久留置時，先依本局實際結果完成履歷與狀態寫回，再把角色最終狀態明確標在角色卡；不得直接刪除角色資料。

## 6. 歷練、社會名譽、升級與其他持續後果

角色的歷練類別、等級差折算、升級需求與升級後成長，以 `遊玩規則/角色/升級與武學成長.md` 為唯一核心來源；俠名、惡名、名氣與相對名譽以 `遊玩規則/角色/社會名譽與門派.md` 為唯一核心來源。按以下次序逐名計算：

1. 讀取本結局明列的基礎歷練 tag／點數、社會名譽倍率，以及劇本建議角色等級上限 **H**；
2. 依第 3 節確定該角色適用完整結局歷練或個人基礎歷練；
3. 以結算前角色等級 **L** 與 **H** 作角色等級折算：先折算基礎總歷練並向下取整，再依核心規則把整數點分回原有 tag，不新增劇本原本沒有的 tag；把這一步折算後、任何個人額外歷練加成前的總數記為 **E**；
4. **以 E 計算社會名譽**：先依第 6.1 節計算俠名、惡名及每個相對名譽對象的點數增減，再重新推導名氣與所有相關級別；這一步先於歷練型絕活／背景等個人額外歷練加成；
5. 折算完成後，才套用歷練型絕活、背景或其他正式個人歷練加成；只有折算後仍實得至少 1 點某 tag，才視為本次取得該 tag；
6. 把最終歷練加入該角色歷練池；
7. 若達下一級需求，逐級扣除、升級並取得每級依法提供的能力、氣血與外功等級點，直到剩餘歷練不足；不需玩家選擇的成長立即套用；
8. 能力值提升／絕活、每級氣血增加方式／結果及其他規則明定在下一劇本前必須完成的選擇，寫入角色卡中文「待處理更新：必須處理」；若某正式規則明文允許延後且不影響下一劇本合法性，才可寫入「待處理更新：容後處理」；
9. 外功等規則允許保留的點數另記累積／已投入／未分配，不視為待處理更新，也不強迫全部投入；
10. 同步計入本結局造成的人情、恩義、仇怨、債務、懸賞、承諾、師承與武學來源、各來源傳承上限及有效／持有狀態、保留／可修上限、尚需前提、入門與修習段進度、傳承資格、長期傷患及其他跨劇本後果。

### 6.1 社會名譽結算

對每名 PC，使用同一個 E：

- 劇本結局的**俠名倍率** `h` 必須在 `0.0–1.0`；`俠名增加 = E × h`；
- **惡名倍率** `e` 必須在 `0.0–1.0`；`惡名增加 = E × e`；
- 每個正式相對名譽對象 `T` 的倍率 `r_T` 必須在 `-1.0–+1.0`；`相對名譽(T)變化 = E × r_T`。

所有結果四捨五入至 **0.1 點**。

俠名與惡名可以同時增加，而且**都不得因結局扣減**。角色做了新的惡事不會刪除舊俠名，做了新的俠義事也不會洗掉舊惡名。

相對名譽則是淨值，可同一結局對不同正式對象一升一跌；同一對象的新正負點數直接加到該對象目前淨點數。

名氣不接受獨立倍率：

**結算後名氣總點數 = 結算後俠名總點數 + 結算後惡名總點數。**

更新總點數後，依 `遊玩規則/角色/社會名譽與門派.md` 重新計算俠名級、惡名級、名氣級；每個相對名譽對象則用 `內容庫/相對名譽對象.md` 登錄的正式 `c` 與共用 `k` 計算有號級別。

若劇本寫了未在 `內容庫/相對名譽對象.md` 登錄的對象、劇本自行改 c／k、直接給名氣、給俠名／惡名負值，或仍使用 `名望 +1／聲譽 +/-1／勢力關係 +/-1／口碑 +1`，結算視為**劇本規格錯誤**：不得由 GM 臨場猜測換算。保持 `settling`，在遊戲階段外修正劇本／Handbook 或依正式版本化校正流程處理。

若 E=0，所有以 E 為基礎的社會名譽點數變化為 0；已在世界內成立的人情、仇怨、懸賞、犯罪或承諾仍照實保存。

### 6.2 傳播因果

倍率由劇本已寫明的世界傳播與受眾評價決定，不是 GM 在結算時重新作善惡評分。若某事件實際沒有達成劇本倍率的公開／傳播成立條件，使用該結局已寫明的對應變體；不得因 GM 個人欣賞或不滿玩家手段而臨時提高／降低倍率。

**H 不因臨場微調自動改變。** 只增減敵人數量、氣血、AC、DC 或危機速度時，仍使用劇本原本的 H。只有開團前已把整份劇本的對手層級、資源壓力、局勢複雜度、風險、可承擔後果與獎勵實質重新校準為另一正式等級版本，並記錄新建議等級／H、歷練基準等級 R 與相應基礎歷練，才用新版數值。

**歷練與社會名譽都不是 GM 的道德評分。** GM 不得因認為某結局「壞」「失敗」或「不夠英雄」而自行扣減劇本已寫明的歷練，也不得自行扣俠名／惡名。帶走長期傷患、仇怨、債務或其他負面後果的苦澀結局，也不因後果負面而自動少給歷練。

若是未預寫但因果成立的衍生結局，參照最接近的已寫結局，按實際經歷、難度、風險、重大決策與持續後果推導歷練；保存 `derived_from_ending_id`、原始 tag／點數、逐項調整及理由。社會名譽亦參照最近預寫結局的倍率結構，但必須按實際公開程度、傳播鏈與各正式受眾利益逐項推導並保存理由；不得臨場創造新相對名譽對象。不得按道德好壞評分，也不得以故意自殘或製造無關負面狀態刷歷練／名譽。

## 7. 江湖履歷寫回資料

每次正式結算，不論完成、失敗、任務放棄或提前撤離，都要為每名實際參與 PC 產生一筆本局江湖履歷的正式寫回資料；角色卡欄位使用 `GM規則/角色卡格式.md` 的「江湖履歷格式」，實際寫入依 `GM規則/角色卡更新.md`。

### 7.1 GM 內部防重複鍵

GM／結算工作紀錄以 `game_id` 作同一次正式結算的內部唯一鍵：

- 同一次結算重試只校正或完成原紀錄，不建立第二次結算；
- `game_id` 不等於重跑許可，也不得用新 `game_id`、劇本改版、失敗或 0 歷練抹去原履歷；
- 校正或完成本局待處理更新時，仍用原 `game_id` 與目前有效 `receipt_version` 定位原結算。

### 7.2 寫入角色卡的江湖履歷

角色卡**不寫 `game_id` 或 `receipt_version`**。每筆只保存玩家可見、跨劇本仍有用途的內容：

- 劇本正式名稱、版本／來源；需要重跑核對且已有正式劇本識別時，可用中文欄位「劇本識別」保存其值；
- 中文重跑政策；
- 結算類型；
- 玩家可見結局名稱／重要變體；
- 結算日期及可靠的遊戲內日期；
- 本局實得歷練；
- 俠名／惡名／相對名譽變化；
- 玩家已知、會跨劇本延續的持續後果。

角色死亡、退休、失蹤、被俘或永久留置仍先寫本局履歷，再標示最終角色狀態。只寫玩家已知資料，不包含未公開真相、隱藏身份、未發現線索或其他 GM 私密資訊。

舊劇本缺少 `script_id` 或 `ending_id` 時，以正式名稱、版本／來源、正式檔案識別或結局標題建立 GM 內部可稽核對應，不為了補齊角色卡而猜造英文 ID。舊制名望／聲譽／勢力關係若無正式遷移依據，保留舊文字而不猜算新制點數。

角色卡不得因校正結算、重新輸出或完成待處理更新而重複追加同一次江湖履歷；如何確認「同一次」由 GM 內部 `game_id`／憑證版本與儲存系統負責。

## 8. 玩家可見結算憑證

每次正式結算都產生一份以 `game_id` 為主鍵的 `settlement_receipt`。第一份正式版本為 `receipt_version: 1`。**結算憑證可以保存這些識別；角色卡不需要重複抄寫。**

憑證至少包含：

- `game_id`、`script_id`、劇本名稱／版本／來源、結算日期及遊戲內結束時點；
- 本局有效 `replay_policy` 與 `continuity_mode`；若下一段明確連續，列出玩家可見的 `continuity_handoff` 來源及須帶入短期資源／狀態；
- Handbook 可重現版本及凍結所用 `save_version`；
- 結算類型、`ending_id`、玩家可見結局名稱／變體及已公開直接世界後果；衍生結局另列玩家可見推導結果；
- 每名 PC 的 `participation_record`、結算資格及歷練依據；
- 物質得失清單、應收未收項目、共有財產 `shared_asset_id`、玩家分配決定及目前保管狀態；
- 每名 PC 結算前、增減、結算後的等級、歷練池、實得歷練 tag、銀兩、裝備、重要狀態、俠名、惡名、名氣、所有有變化的正式相對名譽、人情／恩義／仇怨／懸賞／債務／承諾、武學來源／上限／修習狀態及角色最終狀態；
- 社會名譽計算的 E、各倍率、0.1 點取整結果與重新推導的級別；
- 新增、更新或解除的長期特殊傷患及其來源；
- 每名 PC 的**待處理更新，分列「必須處理／容後處理」**，以及外功等級點累積／已投入／未分配和下一劇本入場完整性；
- 發出時間、玩家核對狀態、`correction_log` 及 `advancement_resolution_log`；
- `delivery_manifest`：每個正式下載產物的穩定檔案識別／路徑、檔名、格式、適用 PC／閱聽範圍、`receipt_version`、交付方式、權限及可用狀態；後端提供時另記內容校驗值。不得把會失效的短效下載 URL 當成唯一識別。

GM 先向玩家展示暫定摘要，讓玩家核對事件記錄、數值計算、物品總量、所有權與自己的分配／成長選擇。玩家提出具體矛盾時，回查凍結存檔、劇本及規則後改正。玩家暫時無法回應時可標記「未確認」並完成基本交付，但 GM 不得替他作財產分配或必選升級決定；財產維持共同持有／原有權利，未完成必選項記為「必須處理」。合法未分配外功點不屬阻擋項目。

### 8.1 完整檔案與玩家下載交付

聊天摘要、差異清單、程式碼區塊、畫面預覽或一句「角色卡已更新」都不能取代正式交付。每次結算至少產生並開放以下檔案：

- 每名實際參與 PC 各一份**完整、更新後角色卡**；由 `GM規則/角色卡更新.md` 生成並驗證，不得只交增減差異或只修改 GM 端副本。角色卡內容不包含 `game_id`／`receipt_version` 等後端識別；角色卡檔名也不要求包含它們，可用角色名稱與日期／一般版本標記區分；
- 一份完整玩家可見 `settlement_receipt`，可以全隊共用或依玩家分拆，但不得包含 `settlement_record` 的 GM 私密資料；結算憑證檔名可使用 `game_id`／`receipt_version` 以便版本管理；
- 角色卡與結算憑證都必須可由玩家重新開啟；建議角色卡以 UTF-8 Markdown 為主，亦可另附 JSON 或 PDF。

AI GM 使用 `opening_environment` 已確認的 `player_delivery_method`／`player_delivery_target`，或由宿主在結算階段明確批准的等效位置。可用方式包括對話中的可下載檔案、玩家獲授權的 ChatGPT Library／Google Drive 檔案、repo artifact 或其他持久位置；若對話檔案本身不是持久項目，仍須把正式產物保存在已批准的持久 target。每名玩家只需獲取自己有權查看的角色卡及玩家可見憑證；不得為此分享 GM 私密 game save、`settlement_record` 或其所在資料夾／namespace。

正式交付前，AI GM 必須逐一重新開啟並讀取下載產物，核對它們與已寫回的角色卡及 `settlement_receipt` 一致，並確認附件可下載或目標檔案的玩家權限有效。每個產物在 `delivery_manifest` 標為 `available_unconfirmed` 或 `download_confirmed` 才算已開放；玩家暫時未回應可以是前者，不必假稱已實際下載。任何產物為 `failed`、缺少完整檔案、只有摘要或玩家無權存取時，結算維持 `settling`，不得關閉或清理最後有效 save。

## 9. 結算後角色卡更新窗口、校正與待處理更新

本文件負責決定結算變更及 `settlement_receipt` 的版本；**所有既有角色卡的實際修改、重算、完整卡驗證與交付統一依 `GM規則/角色卡更新.md`。**

### 9.1 固定結算後更新窗口

當本局 `receipt_version: 1` 已定稿、基本結算結果已依 `角色卡更新.md` 寫回，而且每名玩家已可取得本局第一份完整更新後角色卡與結算憑證後，GM／AI GM **必須逐名主動提供一次角色卡更新窗口**。

對每名角色：

1. 先列出「必須處理」；
2. 再列出「容後處理」；沒有任何待辦時只告知「無待處理更新」；
3. 有待辦時，詢問玩家哪些要現在處理；
4. 玩家宣告「現在處理」時，依 `GM規則/角色卡更新.md` 取得玩家選擇／擲骰並更新完整角色卡；若來自本次結算，同時在 GM 內部依原 `game_id` 版本化更新 `settlement_receipt` 與 `advancement_resolution_log` 等相應紀錄；
5. 完成後重新產生、讀取並驗證受影響的完整角色卡與憑證；舊版本標為 `superseded`，目前有效版本寫回 `delivery_manifest`；
6. 玩家宣告延後「必須處理」時，角色卡及憑證保留該待辦，並清楚標示「下一新劇本前必須完成」；這**不阻擋本次結算關閉**；
7. 玩家宣告延後「容後處理」時，照常保留，且不產生下一劇本入場阻擋；
8. 玩家暫時沒有回應時不得代選；保留原類別，本次結算仍可關閉。

合法可保留的未分配外功點等不屬待處理更新，不因本窗口而變成必須花費的項目。窗口亦不是免費重配；只可處理已正式存在、具有合法來源的待辦。

### 9.2 結算校正與後續完成

正式憑證只可版本化校正，不得無痕覆寫。每次結算校正：

- 遞增 `receipt_version`；
- 在 `correction_log` 保存時間、原因、依據、舊值與新值；
- 用 GM 內部 `game_id` 定位原結算，產生要交給 `角色卡更新.md` 的受影響角色欄位與新憑證版本；**角色卡不新增 game／receipt ID 欄位**；
- 角色卡更新完成後，重新產生並驗證所有受影響的可下載角色卡／憑證，更新 `delivery_manifest`，並把舊產物明確標為 `superseded`，不得讓多個版本同時冒充目前有效版本；
- 沒有可核對依據時不得猜測補寫。

舊角色卡若只有舊制 `名望／聲譽／勢力關係／口碑`，沒有逐局可稽核事件與正式遷移表時，**不得用單一數學公式猜測轉成俠名／惡名／相對名譽**。保留舊值與來源文字，待 Handbook 另有正式 migration 規則或逐筆履歷可核對後，才依 `GM規則/角色卡更新.md` 版本化校正。

玩家在結算後窗口或日後合法遊戲階段外完成待處理更新時，依 `GM規則/角色卡更新.md` 取得玩家選擇／擲骰並重算角色卡；若該待辦來自既有結算，同時遞增原憑證版本，在 `advancement_resolution_log` 保存完成時間、玩家選擇、擲骰結果（若有）及所有連動數值。這是完成已取得的更新，不寫入 `correction_log`，也不建立新 `game_id`。

若本局已關閉且仍有待處理更新，下一次 `GM規則/開局檢查.md` 必須在正式資格檢查前先提供開局前角色卡更新窗口；其中「必須處理」必須清除才可入場，「容後處理」可以繼續保留。不得在遊戲進行中臨時搜尋舊紀錄、代替玩家選擇或把未完成選項當作可即時啟用的資源。

## 10. 固定結算次序、交付與存檔清理

結算必須依序執行：

1. **凍結來源**：保存最後有效 `game_id`／`save_version`，停止以遊戲行動改動本局，記錄劇本及 Handbook 版本；
2. **確認結局**：確定結算類型、`ending_id`、變體、結束時點與直接世界後果；
3. **確認參與**：逐名建立 `participation_record` 及資格，不轉移替補角色資格；
4. **盤點實際得失**：分類已取得、應收未收、暫時保管、共同持有及未取得／失落；玩家處理可分配財產，未決項目維持共有；
5. **計算個人結算**：先作角色等級歷練折算取得 E，再按劇本倍率計算俠名／惡名／相對名譽並推導名氣，之後才套歷練個人加成、逐級升級、長期特殊傷患與所有其他持續後果；分開「必須處理／容後處理」與可保留未分配點數；
6. **建立並核對摘要**：從同一凍結來源建立 `settlement_record` 及暫定 `settlement_receipt`，展示結局、參與、物質分配與每名 PC 的「結算前 → 增減 → 結算後」；
7. **定稿第一版憑證**：處理有依據的核對錯誤，發出 `receipt_version: 1`；未回應者標記「未確認」，不替其作選擇；
8. **寫回基本結算角色卡**：只定位本 `game_id` 明確綁定且列入參與紀錄的 PC 角色卡，把正式憑證與本局寫回資料交給 `GM規則/角色卡更新.md`，逐張完成受控更新 transaction；角色卡只寫中文玩家欄位，不抄後端 ID；
9. **驗證第一版寫回與交付**：確認每張完整角色卡已重新讀取並通過 `角色卡更新.md` 與 `角色卡格式.md` 的一致性硬檢，且實際角色結果與正式憑證一致；依第 8.1 節開放完整角色卡與憑證並建立 `delivery_manifest`；
10. **提供結算後更新窗口**：依第 9.1 節逐名詢問是否現在處理「必須處理／容後處理」。選擇處理者完成更新、必要時遞增憑證版本並重新驗證；選擇延後或無回應者保留原類別；
11. **最終驗證、開放並關閉**：重新讀取每個目前有效正式檔案，確認內容、版本及玩家存取／下載方式有效；全部至少為 `available_unconfirmed`，而更新窗口亦已提供並記錄結果後，才把本局標記 `closed` 並清理進行中動態存檔。

**清理範圍**：本次流程使用的 `OOTB_Save_<game_id>` 活躍狀態、自動存檔、檢查點、暫存快照及只為繼續本劇本而存在的 GM 動態狀態。後端支援刪除時，在交付成功後刪除；不支援時至少標記 `closed` 並從「可續跑中的遊戲」索引移除。不得為清理而列舉其他 `game_id`。

若 `GM規則/開局環境.md` 記錄採用 GitHub 臨時 game save branch，只依 `opening_environment` 內的 `storage_cleanup_policy` 處理：正式憑證及須保留紀錄已在 host 認可的持久位置可重新讀取後，才可刪除臨時 branch；若以該 branch 保留 closed record，則標記 `closed`、從活躍遊戲索引移除並停止寫入。不得為了關閉本局把動態 game save 合併進 default branch，也不得碰觸其他 branch。Google Drive、ChatGPT Library 或其他方案同樣只清理本 `game_id` namespace／save 項目，不擴張至同資料夾／Library／project 的其他內容；Library 方案不得刪除或覆蓋已列入 `delivery_manifest` 的玩家下載產物。

**不得清理**：已更新角色卡、正式 `settlement_receipt`、`delivery_manifest` 及其中目前有效的玩家下載產物、`correction_log`、`advancement_resolution_log`、仍未完成的待處理更新、未分配點數、剩餘歷練池、俠名／惡名／名氣／相對名譽與合法成長；已宣告連續運行時亦不得清除必要的 `continuity_handoff`。正式憑證須在本 `game_id` 的 closed record 或 host 認可的持久結算位置保存，但不留在活躍遊戲索引。

若憑證生成、`角色卡更新.md` 的寫回 transaction、完整下載檔案生成、重新讀取驗證或玩家存取開放任何一步失敗，**不得刪除最後有效 game save**。保留凍結來源並維持 `settling`，直至正式憑證及所有本局角色卡都有已驗證且玩家可存取的完整下載產物。單純因玩家在第 9.1 節延後待處理更新，或暫時未回應更新窗口，不屬結算交付失敗。

單次獨立劇本關閉後再開同一劇本，仍須通過 `GM規則/開局檢查.md` 的開局前更新窗口、角色卡及重跑履歷檢查。若劇本只是長篇戰役中尚未完成的同一持續流程，保留同一 game save；只有該章本身被定義為獨立完整流程時，才正式結算並關閉其 `game_id`。
