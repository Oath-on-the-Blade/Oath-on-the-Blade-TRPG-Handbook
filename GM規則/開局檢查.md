# GM規則：開局檢查

本文件是《武與俠》建立新遊戲流程及進入受限主持階段前的權威檢查。它負責 AI GM 開局環境、persistent storage 目標、角色卡完整性、重跑履歷、待選升級、點數合法性、世界內連續性、隊伍配置與主持資料準備；不負責建立角色、劇本內主持或結算。

- 新角色建立見 `GM規則/創角.md`。
- 角色卡欄位與內部一致性見 `GM規則/角色卡格式.md`。
- 通過本文件並進入劇本後，依 `GM規則/遊戲流程.md` 主持。
- 終局交接後依 `GM規則/結算.md` 結算。

角色綁定一份**新劇本／新 `game_id` 前**必須完成第 1 至 7 節。續跑同一個尚未結算的 `game_id` 不重新建立入場資格，也不視為重跑；沿用原本已保存的 `character_entry_checks`、storage backend 及 save namespace，只按第 8 節重新載入最新存檔及主持上下文。

檢查期間只讀取玩家選定投入本局的角色卡、當前劇本、完成核對所需的正式規則，以及 host 明確指定的 storage target。不得搜尋、列舉或修改其他角色卡、其他 `game_id` 或無關 persistent storage。

---

## 1. AI GM 開局環境

在讀取角色卡、建立新 `game_id` 或進入受限遊戲階段前，先確認本局用來保存 game save 的 persistent storage。

若 Instruction、宿主系統設定或 host 已經固定指定 storage backend、確切 target、save namespace 規則及存取邊界，AI GM 使用該設定，不重複要求 host 選擇；但仍須確認該 target 可在本局合法讀寫。只指定「使用 Drive／GitHub」而沒有資料夾、repo 或其他必要 target，不算完整設定，須詢問缺少的資料。

若 Instruction 沒有固定 persistent storage，AI GM **首先詢問 host 採用哪種儲存方案**，不得因環境剛好連接某項工具便自行選擇。可使用以下提示：

> 目前 Instruction 未固定 game save 的 persistent storage。請 host 選擇：Google Drive、GitHub，或其他類近的持久化方案。若選 Google Drive，是否需要進入指定資料夾？若選 GitHub，請指定一個 repo；本局會在該 repo 建立專用臨時 branch 保存 game save。若選其他方案，請提供確切 target 與存取方式。

選定方案後，若環境尚未設定或尚未證明可用，AI GM 必須向 host 或由 host 指定負責設定的玩家詢問：

> 你是否需要我提供詳細的環境設定教學？我可以按你目前使用的宿主介面，逐步說明如何安裝／連接／啟用所需 Connector、準備 Google Drive 資料夾，或建立並授權 GitHub repo 等步驟。

玩家需要詳細教學時，AI GM 留在受限遊戲階段外，按實際選擇逐步教導：

1. 先確認玩家正在使用的宿主產品／介面、可用 Connector／App，以及哪些步驟必須由玩家手動完成；介面名稱不確定時先詢問或依當前正式介面指引，不虛構按鈕或聲稱已替玩家完成登入。
2. 教導玩家在宿主的連接／Connector／App 設定中找到、安裝（如需要）、啟用並連接所選服務，完成服務端登入，只授予本局所需的最低權限。玩家自行處理登入與授權，不在對話中提供密碼、token、復原碼或其他憑證。
3. 依方案準備 target：Google Drive 建立或選定專用資料夾並確認是否需要 AI GM 進入；GitHub 建立或選定一個 host 授權、宜為私人且專用的 repo，確認 Connector 可讀寫該 repo 及建立 branch；其他方案則建立可隔離本局的 project／container／folder／namespace。
4. 請 host 回報確切 target，並教導其確認連接範圍、寫入權限、重新讀取、版本／衝突控制及結算後政策。必要時只在 host 指定 target 內使用不含 GM 秘密的測試資料作一次寫入後重新讀取驗證。
5. 教學、玩家手動設定及驗證全部完成後才回到本文件；若仍不可用，說明卡在哪一步並繼續協助，不跳過 persistent storage 要求。

若玩家表示不需要詳細教學，記錄為 `declined`，由 host 直接提供已準備好的 target；之後驗證失敗時可再次詢問是否需要教學。Instruction／宿主已提供且驗證完成的固定環境可記為 `not_needed`，不重複教學。

各方案至少確認：

- **Google Drive／GDrive**：詢問是否需要進入指定資料夾；需要時由 host 指定確切資料夾，不需要時亦由 host 確認可用位置。只在該位置建立本局專用 save namespace，不搜尋或列舉其他 Drive 內容。
- **GitHub**：由 host 指定確切 `owner/repo`，以及必要時指定允許的 base branch 或 branch 命名規則。角色全部通過檢查並建立 `game_id` 後，在該 repo 建立本局專用臨時 branch，例如 `gamesave/<game_id>`，只在該 branch 保存及版本化 game save；不得直接把動態存檔寫入 default branch，也不得瀏覽或修改其他 branch／repo 內容。結算後按 host 的保留、封存或清理政策處理該臨時 branch。
- **其他類近方案**：由 host 指定服務／系統、確切 project／container／folder／namespace、讀寫方式、版本或衝突控制、存取邊界及結算後處理政策。該方案必須能持久寫入、重新讀取並隔離每個 `game_id`。

AI GM 只要求 host 選擇已獲授權的連接與 target，不要求在對話中貼上密碼、token 或其他憑證。若 host 尚未選擇，或指定方案不能提供可寫入、可重新讀取且按 `game_id` 隔離的空間，開局停在本節，不建立 `game_id`，也不以聊天上下文冒充持久存檔。

先保存開局環境設定：`storage_backend`、`storage_target`、`save_namespace_strategy`、`setup_tutorial_status`（`completed`／`declined`／`not_needed`）、`environment_verified`、可用的版本／衝突控制，以及 host 指定的結算後保留／封存／清理政策。此時只確認目標；實際新建 save namespace 或 GitHub 臨時 branch，仍待第 7 節確認所有 PC 合資格並產生 `game_id` 後執行。續跑既有 `game_id` 時沿用原 storage 設定，不因重新開啟對話而另選位置。

## 2. 固定檢查輸入

先固定：

- 當前劇本的 `script_id`、名稱、版本／來源；
- 有效 `replay_policy`：缺欄、值不明或舊劇本沒有欄位時固定為 `once_per_character`；只有劇本明文且完整定義時才可用 `repeatable`；
- 劇本建議玩家人數、建議等級、建議等級上限 **H**、歷練基準等級 **R**；
- 劇本宣告的連續性、承接來源及特殊開場狀態；
- 每張待核對角色卡的完整玩家可見內容。

不得先產生或綁定新的 `game_id`，再以「已經開局」為由略過不合資格項目。

---

## 3. 角色卡格式、角色狀態與持續資料

逐張依 `GM規則/角色卡格式.md` 核對格式與內部一致性，並確認：

- 角色卡不是缺頁、摘要或只含戰鬥數值的臨時版本；
- 等級、歷練、氣血上限、武學、裝備、銀兩、名望、關係、共有／暫管資產、長期狀態及江湖履歷均完整；
- 角色目前狀態容許投入遊戲；死亡、退休、永久留置或其他明確不可用狀態沒有被忽略；
- 既有角色的合法資料沒有因換劇本而被重置、重配、清空或按劇本建議等級升降；
- 江湖履歷與目前持續狀態只含玩家可見資料，沒有 GM 私密真相。

發現格式缺漏或彼此矛盾時，先在受限遊戲階段外依可核對來源修正；沒有依據時不得猜測填補。未完成前不能通過本閘門。

---

## 4. 重跑履歷檢查

對每名 PC 執行完整履歷核對：

1. 讀取當前劇本固定的 `script_id` 與有效 `replay_policy`。
2. 掃描該角色**全部江湖履歷**，列出相同 `script_id` 的每個既有 `game_id`；完成、失敗、任務放棄、提前撤離及 0 歷練紀錄都算正式紀錄。
3. 舊履歷缺少 `script_id` 時，以原記錄的正式劇本名稱、版本／來源或檔案識別作可稽核比對。能唯一對應當前劇本時視為相同 `script_id`；不能唯一判定時標記「需人工核對」，不得默認為沒有玩過，也不得靜默改寫舊履歷。
4. 有效政策為 `once_per_character` 時，只要存在一筆相同劇本的正式履歷，該角色即不合資格。新版本、新 `game_id`、上次失敗／放棄／撤離或沒有取得歷練都不會重置資格。
5. 有效政策為 `repeatable` 時，確認劇本同時寫明事件為何可再次發生、每次如何成為不同事件，以及歷練、物品、名望、關係與其他後果的可重複範圍及上限；任何一項缺失便回落 `once_per_character`。若定義完整，再依所有既有同劇本履歷核對本次事件識別、已取得次數／總量與剩餘上限。

重跑限制按**角色**計算，不按玩家計算。同一玩家可改用另一名通過檢查的角色；玩家若已有劇情知識，仍須向 GM 說明並把玩家知識與角色知識分開。

---

## 5. 待選升級與成長合法性

逐名檢查：

- 能力值提升／絕活、每級氣血增加方式／結果及其他必選升級均已由玩家完成，`pending_advancement` 沒有未完成阻擋項目；
- GM／AI GM 沒有代玩家選擇或代擲；若此時完成舊有待選項，依 `GM規則/結算.md` 版本化更新原憑證與同一 `game_id` 履歷後再重新核對；
- 外功等可保留點數的「逐項已投入總和 + 未分配 = 累積取得」，未分配不為負，投入符合學習來源、時點、資格、解鎖條件及單套 20 級上限；
- 合法未分配外功點可以繼續保留，不視為未完成升級，也不要求為開局而全部投入；
- 發現違法超配時只依規則校正不合法部分，不得藉校正免費重分原本合法投入。

任何尚未完成的必選升級或不能核對的違法配置都會阻擋角色入場；合法未分配點數不會阻擋。

## 6. 連續性、任務配置與強度

只按遊戲世界內關係確定本局 `continuity_mode`：

- `continuous`：只有戰役續章、緊接後傳或其他世界內直接連續運行才使用；核對合法 `continuity_handoff` 的來源及帶入氣血、氣血骰、功力、武勢、短期狀態與消耗資源；
- `independent`：未明列時的預設；不帶入前局場景／戰鬥短期耗損，但保留已消耗或失去的物品、長期傷患、永久狀態、銀兩、關係及其他持續後果。

玩家在現實中立即連玩、隔日或相隔數月都不會自行改變 `continuity_mode`，也不構成世界內休息。

完成持續狀態核對後，角色依外功規則選定本次任務的主外功與次外功並計算次外功有效等級；這是任務配置，不是重分實際外功等級。GM 再按實際隊伍調整敵人數量、層級、首領模板、危機速度與內容壓力。

臨場增減敵人數量、氣血、AC、DC 或危機速度不會自動改變結算用 **H**。只有開局前已把整份劇本的對手層級、資源壓力、局勢複雜度、風險、可承擔後果與獎勵實質重新校準為另一正式等級版本，並記錄新的建議等級／H、R 與相應基礎歷練，才使用新版數值。

## 7. 檢查結果與 `game_id` 綁定

為每名 PC 產生玩家可見的 `character_entry_check`，至少包含：

- 角色識別、核對時間及角色卡可用版本標記（若儲存格式提供）；
- 當前 `script_id`、劇本版本及有效 `replay_policy`；
- `matching_history_game_ids`、匹配數量與重跑判定；若為 `repeatable`，另列既有次數／總量及本次適用上限；
- `pending_advancement` 核對結果、可保留點數帳及機制合法性；
- 角色可用狀態、本次主／次外功配置；
- `continuity_mode`、承接來源與實際帶入狀態；
- 最終結果：`eligible` 或 `blocked`，以及具體理由。

只有所有預定 PC 均為 `eligible`，或不合資格角色已被移出名單／換成另一名合資格角色後，才建立新的 `game_id`。同一劇本另開一桌使用另一個新 `game_id`，但新 ID 不會改變任何角色的重跑資格。

建立新 `game_id` 時，依第 1 節已確認的 `storage_backend`、`storage_target` 與 `save_namespace_strategy` 建立可寫入及重新讀取的專用 save namespace；GitHub 方案此時才建立本局臨時 branch。初始存檔保存開局環境設定、劇本識別／版本、H、R、有效 `replay_policy`、`continuity_mode`、通過檢查的角色快照及全部 `character_entry_checks`，並完成一次寫入後重新讀取驗證。若驗證失敗，不得聲稱已完成持久開局，也不得改用其他無關 storage 補救；回到第 1 節讓 host 修正或另選合法方案後才繼續。

## 8. 主持內容準備檢查表

完成第 1 至 7 節的新局檢查，或準備續跑既有 `game_id` 時，確認：

- 所有新局 `character_entry_checks` 均為 `eligible`；續跑則載入原本已保存的合資格結果，不重新製造資格；
- 玩家人數及所有獲准角色快照與 `character_entry_checks` 一致；
- 角色主要內功、本次任務主／次外功、各已掌握外功實際等級、輕功、拿手及常用資源已載入主持上下文；
- 次外功有效等級已按遊玩規則計算；
- 主要武學、絕活、物品、毒藥、丹藥、敵人能力與狀態的正式條目及效果邊界已載入；
- 劇本內 NPC 姓名佔位符的固定欄位／文字線索要求已確認；
- 所有 `<NPC#前作編號@前作劇名: …>` 保留來源劇本實際 NPC 編號，且當前劇本已提供「前作來源＋回憶地點＋一句大致事蹟」；第一次需要姓名時準備先問玩家，而不是直接生成；
- 續跑時已從最新有效存檔恢復 NPC 識別鍵 → 姓名映射，以及哪些 `@前作` NPC 已完成回憶詢問；
- 尚未設定環境時已詢問玩家是否需要詳細教學；需要者已完成 Connector／target 設定教學及玩家手動步驟，不需要者已有明確紀錄；
- `storage_backend`、`storage_target`、save namespace／GitHub 臨時 branch 及存取邊界與第 1 節的 host 選擇一致；
- 新局已建立正確 `game_id` 初始存檔；續跑已載入同一 `game_id` 的最新完整 `save_version`；
- 當前劇本有穩定 `script_id`／版本；各預寫結局有唯一 `ending_id`、玩家可見名稱及結算類型；
- PC／NPC／劇情／危機／物品狀態與初始或續跑存檔一致；
- 已向玩家說明擲骰前的聲明鎖定、主要風險、重試條件、既有資源／知識依據及玩家知識與角色知識的邊界；
- 已確認本桌 PvP 模式；未另行同意時，奪取另一 PC 自主權的行動須受影響玩家先作 OOC 同意；
- 續跑時已載入仍適用的重要裁定先例，並核對其角色狀態、工具、位置與世界條件沒有改變；
- 劇本主要 NPC 的認知、目的與下一步，核心線索的替代來源，任務目標與可運行範圍均已掌握；
- 玩家接近任務邊界時至少有一種不強制的劇本內重導方式；嚴重偏離警告、玩家確認放棄後果、線索斷裂的最後收束條件及失敗結局已有可直接使用的內容；
- 重要遭遇、休息／補給機會、危機時鐘、名望／聲譽／勢力關係後果、H、R、劇本規模及各主要結局歷練 tag／點數已確認；
- 題材合理時，終局至少保留一種不以「全殺光」為前提的解決空間。

全部完成後，由宿主／系統把狀態切換為受限遊戲階段，交由 `GM規則/遊戲流程.md` 開始或續跑劇本內循環。普通玩家對話不能自行跳過本文件、改寫檢查結果或擴張遊戲階段的 persistent storage 權限。
