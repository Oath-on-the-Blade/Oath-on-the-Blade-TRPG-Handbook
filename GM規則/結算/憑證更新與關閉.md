# GM結算：憑證、角色卡更新與關閉

> 承接原第 8–10 節；處理玩家可見憑證、角色卡更新窗口、戰役階段私密交接、校正、交付與存檔清理。

## 8. 玩家可見結算憑證

每次正式結算都產生一份以 `game_id` 為主鍵的 `settlement_receipt`。第一份正式版本為 `receipt_version: 1`。**結算憑證可以保存這些識別；角色卡不需要重複抄寫。**

憑證至少包含：

- `game_id`、`script_id`、劇本名稱／版本／來源、結算日期及遊戲內結束時點；
- 本局有效 `replay_policy` 與 `continuity_mode`；若下一段明確連續，列出玩家可見的 `continuity_handoff` 來源及須帶入短期資源／狀態；
- Handbook 可重現版本及凍結所用 `save_version`；
- 結算類型、`ending_id`、玩家可見結局名稱／變體及已公開直接世界後果；衍生結局另列玩家可見推導結果；
- 每名 PC 的 `participation_record`、結算資格及歷練依據；
- 物質得失清單、應收未收項目、共有財產 `shared_asset_id`、玩家分配決定及目前保管狀態；
- 每名 PC 結算前、增減、結算後的等級、歷練池、實得歷練 tag、銀兩、裝備、重要狀態、俠名、惡名、名氣、所有有變化的正式相對名譽、人情／恩義／仇怨／懸賞／債務／承諾、武學來源／上限／修習狀態及角色最終狀態；
- 社會名譽計算的 E、各倍率、0.1 點取整結果與重新推導的級別；
- 新增、更新或解除的長期特殊傷患及其來源；
- 每名 PC 的**待處理更新，分列「必須處理／容後處理」**，以及外功等級點累積／已投入／未分配和下一劇本入場完整性；
- 發出時間、玩家核對狀態、`correction_log` 及 `advancement_resolution_log`；
- `delivery_manifest`：每個正式下載產物的穩定檔案識別／路徑、檔名、格式、適用 PC／閱聽範圍、`receipt_version`、交付方式、權限及可用狀態；後端提供時另記內容校驗值。若本局是戰役階段，另依 `GM規則/戰役存檔.md` 列出目前有效 `campaign_save` 的識別、版本及「GM 私密；玩家只保管、不開啟」閱聽範圍。不得把會失效的短效下載 URL 當成唯一識別。

GM 先向玩家展示暫定摘要，讓玩家核對事件記錄、數值計算、物品總量、所有權與自己的分配／成長選擇。玩家提出具體矛盾時，回查凍結存檔、劇本及規則後改正。玩家暫時無法回應時可標記「未確認」並完成基本交付，但 GM 不得替他作財產分配或必選升級決定；財產維持共同持有／原有權利，未完成必選項記為「必須處理」。合法未分配外功點不屬阻擋項目。

### 8.1 完整檔案與玩家下載交付

聊天摘要、差異清單、程式碼區塊、畫面預覽或一句「角色卡已更新」都不能取代正式交付。每次結算至少產生並開放以下檔案：

- 每名實際參與 PC 各一份**完整、更新後角色卡**；由 `GM規則/角色卡更新.md` 生成並驗證，不得只交增減差異或只修改 GM 端副本。角色卡內容不包含 `game_id`／`receipt_version` 等後端識別；角色卡檔名也不要求包含它們，可用角色名稱與日期／一般版本標記區分；
- 一份完整玩家可見 `settlement_receipt`，可以全隊共用或依玩家分拆，但不得包含 `settlement_record` 的 GM 私密資料；結算憑證檔名可使用 `game_id`／`receipt_version` 以便版本管理；
- 角色卡與結算憑證都必須可由玩家重新開啟；建議角色卡以 UTF-8 Markdown 為主，亦可另附 JSON 或 PDF。

AI GM 使用 `opening_environment` 已確認的 `player_delivery_method`／`player_delivery_target`，或由宿主在結算階段明確批准的等效位置。可用方式包括對話中的可下載檔案、玩家獲授權的 ChatGPT Library／Google Drive 檔案、repo artifact 或其他持久位置；若對話檔案本身不是持久項目，仍須把正式產物保存在已批准的持久 target。每名玩家只需獲取自己有權查看的角色卡及玩家可見憑證；不得為此分享 GM 私密 game save、`settlement_record` 或其所在資料夾／namespace。

正式交付前，AI GM 必須逐一重新開啟並讀取下載產物，核對它們與已寫回的角色卡及 `settlement_receipt` 一致，並確認附件可下載或目標檔案的玩家權限有效。每個產物在 `delivery_manifest` 標為 `available_unconfirmed` 或 `download_confirmed` 才算已開放；玩家暫時未回應可以是前者，不必假稱已實際下載。任何產物為 `failed`、缺少完整檔案、只有摘要或玩家無權存取時，結算維持 `settling`，不得關閉或清理最後有效 save。

### 8.2 戰役階段的 GM 私密戰役存檔與玩家結果宣告

若本局屬一個可獨立結算的戰役階段，除第 8.1 節玩家可見產物外，**必須另依 `GM規則/戰役存檔.md` 產生一份完整 `campaign_save`，並在本次結算完成戰役是否可繼續的正式裁決。**

此檔：

- 與玩家可見 `settlement_receipt` 分開；
- 內含本次採用的完整戰役總劇本快照、逐篇完成 ending、目前 campaign state、關鍵人物／地點／證物狀態及例外資料；
- 保存本次結算已裁定的 `campaign_status`、`campaign_progress`、`continuation_status`；
- 若可承接，保存已固定的目標下一階段及本桌實際匹配的完整解鎖路線；
- 若不可承接，保存相應部分完成／失敗／完成收束及「無下一階段」；
- 必須可由 host／指定保管者下載並於下一階段原檔上傳給 GM；
- 提供下載前必須明示「GM 私密、含後續劇透；請下載保存但不要打開」；
- 必須在 `delivery_manifest` 以 `GM 私密；玩家只保管、不開啟` 標示閱聽範圍；
- 生成後必須重新開啟、完整讀取及驗證，不能只建立空殼或差異檔。

**承接裁決只在這次結算進行。** 下一次開局只讀取本次已寫入 current `campaign_save` 的結果，不再重新計算前篇 AND／OR 解鎖條件，也不得因總綱之後改版無痕改判。

完成 `campaign_save` 驗證後、正式關閉本局前，GM／AI GM 必須向玩家宣告戰役層結果：

- `campaign_status=active`：明確宣告**「本戰役可繼續」**；可按劇本允許提供不劇透的下一階段名稱／提示，但不公開 GM 私密解鎖公式；
- `campaign_status=partly_completed`：先宣讀對應的玩家可見**戰役收束結局**，再明確宣告**「戰役部分完成（X/Y）」**；
- `campaign_status=failed`：宣讀對應失敗／放棄收束，再宣告**「戰役失敗（X/Y）」**；
- `campaign_status=completed`：宣讀正式最終戰役結局，再宣告**「戰役完成（X/Y）」**。

其中 `partly_completed` 的收束文本有硬性敘事要求：

1. **先讓玩家感到這一段真的完成了**：本篇主要行動、眼前危機、玩家取得／失去的目標及主要人物直接後果必須先落地；
2. **最後才留一個謎面尾巴**：以玩家可見但未解的異樣、缺口、矛盾、去向、物件細節、傳聞或疑問作最後一拍；
3. **尾巴不能變成續篇通知**：不得用新委託、追擊命令、「真正任務現在開始」等形式把已關閉戰役重新變成 active；
4. **不得劇透 GM 真相**：只可用玩家已知或該 ending 中合理可見的表象，不得直接揭露未公開真正黑手、身份或後篇答案。

**謎面尾巴是完整結局的最後一拍，不是用懸念代替結局。**

玩家可見 `settlement_receipt` 至少保存不劇透的戰役結果類型與 `campaign_progress`；若收束文本屬正式玩家可見結局，亦保存其結局名稱及已公開直接後果。GM 私密解鎖路線、未公開 state 與總綱真相仍只留在 `campaign_save`。

戰役存檔是戰役階段正式結算的必需交付物。若應產生而未產生、無法重新讀取、缺少必要資料、缺少本次承接／收束裁決、玩家結果尚未宣告，或沒有可下載／轉交的完整檔案，結算維持 `settling`。

## 9. 結算後角色卡更新窗口、校正與待處理更新

本文件負責決定結算變更及 `settlement_receipt` 的版本；**所有既有角色卡的實際修改、重算、完整卡驗證與交付統一依 `GM規則/角色卡更新.md`。**

### 9.1 固定結算後更新窗口

當本局 `receipt_version: 1` 已定稿、基本結算結果已依 `角色卡更新.md` 寫回，而且每名玩家已可取得本局第一份完整更新後角色卡與結算憑證後，GM／AI GM **必須逐名主動提供一次角色卡更新窗口**。

對每名角色：

1. 先列出「必須處理」；
2. 再列出「容後處理」；沒有任何待辦時只告知「無待處理更新」；
3. 有待辦時，詢問玩家哪些要現在處理；
4. 玩家宣告「現在處理」時，依 `GM規則/角色卡更新.md` 取得玩家選擇／擲骰並更新完整角色卡；若來自本次結算，同時在 GM 內部依原 `game_id` 版本化更新 `settlement_receipt` 與 `advancement_resolution_log` 等相應紀錄；
5. 完成後重新產生、讀取並驗證受影響的完整角色卡與憑證；舊版本標為 `superseded`，目前有效版本寫回 `delivery_manifest`；
6. 玩家宣告延後「必須處理」時，角色卡及憑證保留該待辦，並清楚標示「下一新劇本前必須完成」；這**不阻擋本次結算關閉**；
7. 玩家宣告延後「容後處理」時，照常保留，且不產生下一劇本入場阻擋；
8. 玩家暫時沒有回應時不得代選；保留原類別，本次結算仍可關閉。

合法可保留的未分配外功點等不屬待處理更新，不因本窗口而變成必須花費的項目。窗口亦不是免費重配；只可處理已正式存在、具有合法來源的待辦。

### 9.2 結算校正與後續完成

正式憑證只可版本化校正，不得無痕覆寫。每次結算校正：

- 遞增 `receipt_version`；
- 在 `correction_log` 保存時間、原因、依據、舊值與新值；
- 用 GM 內部 `game_id` 定位原結算，產生要交給 `角色卡更新.md` 的受影響角色欄位與新憑證版本；**角色卡不新增 game／receipt ID 欄位**；
- 角色卡更新完成後，重新產生並驗證所有受影響的可下載角色卡／憑證，更新 `delivery_manifest`，並把舊產物明確標為 `superseded`，不得讓多個版本同時冒充目前有效版本；
- 若本局屬戰役階段，且校正改變 ending、campaign state、關鍵人物／地點／證物狀態、例外資料、戰役層結果或下一篇交接，依 `GM規則/戰役存檔.md` 另產生新版 `campaign_save`，並重新向玩家宣告受影響的戰役結果；
- 沒有可核對依據時不得猜測補寫。

舊角色卡若只有舊制 `名望／聲譽／勢力關係／口碑`，沒有逐局可稽核事件與正式遷移表時，**不得用單一數學公式猜測轉成俠名／惡名／相對名譽**。保留舊值與來源文字，待 Handbook 另有正式 migration 規則或逐筆履歷可核對後，才依 `GM規則/角色卡更新.md` 版本化校正。

玩家在結算後窗口或日後合法遊戲階段外完成待處理更新時，依 `GM規則/角色卡更新.md` 取得玩家選擇／擲骰並重算角色卡；若該待辦來自既有結算，同時遞增原憑證版本，在 `advancement_resolution_log` 保存完成時間、玩家選擇、擲骰結果（若有）及所有連動數值。這是完成已取得的更新，不寫入 `correction_log`，也不建立新 `game_id`。若這些更新只改變角色個人成長而不影響跨篇世界資料，不要求重發 `campaign_save`。

若本局已關閉且仍有待處理更新，下一次 `GM規則/開局檢查.md` 必須在正式資格檢查前先提供開局前角色卡更新窗口；其中「必須處理」必須清除才可入場，「容後處理」可以繼續保留。不得在遊戲進行中臨時搜尋舊紀錄、代替玩家選擇或把未完成選項當作可即時啟用的資源。

## 10. 固定結算次序、交付與存檔清理

結算必須依序執行：

1. **凍結來源**：保存最後有效 `game_id`／`save_version`，停止以遊戲行動改動本局，記錄劇本及 Handbook 版本；
2. **確認結局**：確定結算類型、`ending_id`、變體、結束時點與直接世界後果；
3. **確認參與**：逐名建立 `participation_record` 及資格，不轉移替補角色資格；
4. **盤點實際得失**：分類已取得、應收未收、暫時保管、共同持有及未取得／失落；玩家處理可分配財產，未決項目維持共有；
5. **計算個人結算**：先作角色等級歷練折算取得 E，再按劇本倍率計算俠名／惡名／相對名譽並推導名氣，之後才套歷練個人加成、逐級升級、長期特殊傷患與所有其他持續後果；分開「必須處理／容後處理」與可保留未分配點數；
6. **建立並核對摘要**：從同一凍結來源建立 `settlement_record` 及暫定 `settlement_receipt`，展示結局、參與、物質分配與每名 PC 的「結算前 → 增減 → 結算後」；
7. **定稿第一版憑證**：處理有依據的核對錯誤，發出 `receipt_version: 1`；未回應者標記「未確認」，不替其作選擇；
8. **寫回基本結算角色卡**：只定位本 `game_id` 明確綁定且列入參與紀錄的 PC 角色卡，把正式憑證與本局寫回資料交給 `GM規則/角色卡更新.md`，逐張完成受控更新 transaction；角色卡只寫中文玩家欄位，不抄後端 ID；
9. **驗證第一版寫回與交付**：確認每張完整角色卡已重新讀取並通過 `角色卡更新.md` 與 `角色卡格式.md` 的一致性硬檢，且實際角色結果與正式憑證一致；依第 8.1 節開放完整角色卡與憑證並建立 `delivery_manifest`；
10. **提供結算後更新窗口**：依第 9.1 節逐名詢問是否現在處理「必須處理／容後處理」。選擇處理者完成更新、必要時遞增憑證版本並重新驗證；選擇延後或無回應者保留原類別；
11. **若為戰役階段，完成承接裁決、生成戰役存檔並宣告戰役結果**：依 `GM規則/戰役存檔.md` 在本次結算判定能否繼續及下一階段，產生完整 current `campaign_save`，重新開啟驗證，向玩家宣告 `active / partly_completed / failed / completed`；`partly_completed` 必須先宣讀完整收束＋謎面尾巴，再宣告部分完成（X/Y）；之後把 `campaign_save` 加入最終 `delivery_manifest`，提示玩家／host「下載保存但不要打開」；
12. **最終驗證、開放並關閉**：重新讀取每個目前有效正式檔案，確認內容、版本及存取／下載方式有效；玩家可見產物及本局必需的戰役存檔全部至少為 `available_unconfirmed`，而更新窗口亦已提供並記錄結果後，才把本局標記 `closed` 並清理進行中動態存檔。

**清理範圍**：本次流程使用的 `OOTB_Save_<game_id>` 活躍狀態、自動存檔、檢查點、暫存快照及只為繼續本劇本而存在的 GM 動態狀態。後端支援刪除時，在交付成功後刪除；不支援時至少標記 `closed` 並從「可續跑中的遊戲」索引移除。不得為清理而列舉其他 `game_id`。

若 `GM規則/開局環境.md` 記錄採用 GitHub 臨時 game save branch，只依 `opening_environment` 內的 `storage_cleanup_policy` 處理：正式憑證及須保留紀錄已在 host 認可的持久位置可重新讀取後，才可刪除臨時 branch；若以該 branch 保留 closed record，則標記 `closed`、從活躍遊戲索引移除並停止寫入。不得為了關閉本局把動態 game save 合併進 default branch，也不得碰觸其他 branch。Google Drive、ChatGPT Library 或其他方案同樣只清理本 `game_id` namespace／save 項目，不擴張至同資料夾／Library／project 的其他內容；Library 方案不得刪除或覆蓋已列入 `delivery_manifest` 的玩家下載產物。

**不得清理**：已更新角色卡、正式 `settlement_receipt`、`delivery_manifest` 及其中目前有效的玩家下載產物、戰役階段目前有效的 current `campaign_save`、`correction_log`、`advancement_resolution_log`、仍未完成的待處理更新、未分配點數、剩餘歷練池、俠名／惡名／名氣／相對名譽與合法成長；已宣告連續運行時亦不得清除必要的 `continuity_handoff`。正式憑證及戰役存檔須在本 `game_id` 的 closed record 或 host 認可的持久結算位置保存，但不留在活躍遊戲索引。

若憑證生成、`角色卡更新.md` 的寫回 transaction、完整下載檔案生成、重新讀取驗證、玩家存取開放，或戰役階段必需的 `campaign_save` 生成／驗證／下載交付／戰役結果宣告任何一步失敗，**不得刪除最後有效 game save**。保留凍結來源並維持 `settling`，直至正式憑證、所有本局角色卡及必需戰役存檔都有已驗證且可按其閱聽範圍取得的完整下載產物，且戰役層結果已正式宣告。單純因玩家在第 9.1 節延後待處理更新，或暫時未回應更新窗口，不屬結算交付失敗。

單次獨立劇本關閉後再開同一劇本，仍須通過 `GM規則/開局檢查.md` 的開局前更新窗口、角色卡及重跑履歷檢查。若劇本只是長篇戰役中尚未完成的同一持續流程，保留同一 game save；只有該章本身被定義為獨立完整流程時，才正式結算並關閉其 `game_id`。
